# `code-development` 规则理由

本文件不参与运行。当前 `SKILL.md`、本文件和现有修改日志都只是核对材料，不自动证明规则正确。

## CD-01 先恢复真实系统和成功条件

- **状态：** `current-effective`
- **行为：** 从真实入口、调用链、数据流、状态和运行事实理解现有系统；外部依赖查看权威来源；明确必须保持的现有行为和可观察结果。
- **理由：** 只读局部文件或按需求字面直接编码，容易在错误 source of truth 上继续工作。
- **案例：** C-14；源码、发布物、说明和体验在局部测试通过后仍不一致。
- **来源：** `SKILL.md`“先理解现有系统”；初始提交 `6a25aa8`；`prompt-lab/subagent-architecture/rule-rationale.md` R25。
- **验证：** 历史失败已观察；具体项目仍需真实入口验证。
- **改变条件：** 从零且没有既有系统时改为先建立最小真实骨架，不能假装存在旧入口。

## CD-02 路线是可证伪假设，先做最小真实切片

- **状态：** `current-effective`
- **行为：** 陌生、跨层或高成本路线先做能沿真实路径体现核心价值的最小切片；Demo 可以粗糙，核心功能必须正确。失败后用最小实验区分局部缺陷与路线问题。
- **理由：** 防止先建完整系统，再用大量条件判断补偿错误路线。
- **案例：** C-05、C-16。
- **来源：** `SKILL.md`“验证路线”“先形成最小核心结果”；`prompt-lab/evolution-map.md`。
- **验证：** 失败案例明确；真实代码类型各异，触发条件不能机械扩大。
- **改变条件：** 明确局部修复且真实入口已验证时不强制另做 Demo。

## CD-03 设计准入取决于当前证据和真实端到端路径

- **状态：** `current-effective`
- **行为：** 在扩大实现前明确接口、数据、状态、失败路径和完成证据；仍依赖后续结果的细节不提前固化。
- **理由：** 大规模实现会放大错误假设；先闭合一条真实路径才能判断架构是否成立。
- **案例：** C-14。
- **来源：** `SKILL.md`“形成能够实现的设计”“按真实路径实现”；初始提交 `6a25aa8`。
- **验证：** 静态规则存在；端到端成效按项目验证。
- **改变条件：** 不为简单、局部、可逆修改制造额外设计文档。

## CD-04 采用最低复杂度并复用成熟能力

- **状态：** `current-effective`
- **行为：** 优先局部修改、现有实现、平台能力、标准库和已有依赖；修根因，删除失效代码，不为一次需求或无证据未来增加配置和结构。
- **理由：** 来自成熟开发经验，减少重复造轮子和长期维护成本；最低复杂度不能破坏已有保护。
- **案例：** C-07；过度抽象曾把有独立作用的成熟判断压成模糊原则。
- **来源：** `MODIFICATION_LOG.md` 2026-08-14；Root Base 的最低复杂度段；Ponytail 工作哲学历史记录。
- **验证：** 用户确认有效；真实代码任务仍需持续观察。
- **改变条件：** 现有能力不满足结果、风险或适配要求时可增加实现，但必须由当前证据支撑。

## CD-05 阶段负责人保留核心判断并把确定执行交下去

- **状态：** `current-effective + unverified`
- **行为：** Code Executor 保留会改变模块设计的判断与核心代码，把读取证据、确定实现、测试和普通修正交给合适执行角色，并吸收报告、返工和验收后一次交回 Root。
- **理由：** 减少 Root 管理阶段细节和高价重复调用，同时利用 Luna 的低成本连续执行。
- **案例：** C-11；Spark 固定合同成功、开放诊断漏项。
- **来源：** `MODIFICATION_LOG.md` 2026-08-27；`agents/PROMPT_HISTORY.md` 2026-08-30；`subagent-architecture/rule-rationale.md` R10、R31。
- **验证：** 静态角色关系已确认；真实成本和质量闭环待验证。
- **改变条件：** 规格已经固定时可直接用执行者；仍需连续阶段判断时不能把责任切成多轮叶子返工。

## CD-06 独立评审按风险决定，并形成返工闭环

- **状态：** `current-effective + unverified`
- **行为：** 误交付风险需要独立判断时提交准确候选、合同、差异和验证证据；Reviewer 给三种结论，Code Executor 负责修正、反驳或补证后复审。
- **理由：** 无条件评审浪费，缺少独立评审又会让实现者自己的假设同时充当验收。
- **案例：** C-15。
- **来源：** `SKILL.md`“按风险进行独立评审”；`code-review`；`agents/PROMPT_HISTORY.md` 2026-08-29。
- **验证：** 静态闭环存在；真实三条结论路径待验证。
- **改变条件：** 低风险、小改动可缩小或省略独立评审，但完成证据不能省略。

## CD-07 分层测试不替代真实宿主和用户路径

- **状态：** `current-effective`
- **行为：** 先做直接具体检查，再覆盖集成、真实宿主、外部服务和用户流程；只声明证据覆盖的层次。涉及可见界面时增加视觉黑盒验证。
- **理由：** 构建和局部测试通过不能证明宿主加载、外部接线和实际使用成立。
- **案例：** C-04、C-14。
- **来源：** `SKILL.md`“分层验证”“交付”；全局验证责任；`agents/PROMPT_HISTORY.md` 视觉黑盒记录。
- **验证：** 历史反例明确；每个项目按真实入口验收。
- **改变条件：** 没有真实环境时只能明确停在静态或影子层，不能删除未验证说明。

## 保护说明

- Demo 规则只针对路线不确定、陌生、跨层或高成本工作，不适用于所有局部修复。
- “成熟做法”和最低复杂度是选择机制，不是必须逐级尝试的固定顺序。
- 真实入口、停止补丁、阶段路由和视觉验收的理由分散在 Prompt Lab；以后改正文必须同时核对本文件列出的来源。
