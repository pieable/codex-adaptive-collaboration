# Code Development

主任务持续掌握用户目标、事实状态、关键设计取舍、跨阶段集成和最终验收。根据改动的风险、依赖和未知程度裁剪流程：明确、低风险的局部修改可以在一次调查、修改和验证中完成；陌生系统、外部依赖、跨模块改动和高风险行为需要明确完成各阶段。

裁剪时参考以下尺度：

- 明确的局部缺陷：复现或确认现象，定位调用链并完成修改；修改后重新运行能够复现或覆盖该缺陷的测试或命令，检查预期输出、状态或行为；
- 陌生外部系统或跨层功能：先调查事实并验证最高风险假设，再打通真实端到端骨架；
- 数据迁移、安全边界或难以回滚的改动：补充设计记录、恢复方案、分阶段实施和独立复核。

## 事实调查与编码准入

从用户要完成的真实任务进入，先区分已证实事实、合理假设和未知项。按当前目标查看项目规则、现有未提交改动和最相关的入口、文档、测试、调用者、数据流与外部依赖，逐步缩小范围。先看项目里是否已有可复用的实现、库或可靠范例；证据已经足以决定方案时停止扩展调查。

正式实现前，以和任务风险相称的精度明确以下内容。简单任务可以用几句话完成，不为通过闸门额外制造文档：

- 用户目标、修改范围和成功标准；
- 当前行为及其直接证据；
- 必须保留的行为、权限和数据边界；
- 相关入口、依赖、主要失败模式，以及需要时的回滚方式；
- 最高风险未知项及其验证方法；
- 能代表真实完成的验收路径。

这些信息中仍有会改变方案的未知项时，继续只读调查或做最小风险实验。实验用于回答一个明确问题，默认可以丢弃；实验结果足以选择实现路线后再进入正式开发。静态推测、mock 成功和代理指标不能代替任务要求的真实系统证据。

外部依赖、API、标准或上游行为有时效性或不确定时，查当前权威来源，包括官方文档、源码、测试、发行记录、包注册表、许可证和安全公告。范围较大或需要多来源取证时交给 `web-researcher`；查询任务说明真实技术栈、版本、现有依赖和必须保持的接口，当前代码负责人结合项目约束作出判断。

## 设计与实施路线

能够解释目标行为、当前行为和二者差异后，画出完成本次改动所需的最小流程、状态转换或数据路径。优先确定信任边界、幂等规则、错误分类和可观察结果。只为影响长期结构、公共接口或多个下游的决定，使用项目已有的设计记录或简短 ADR 保存背景、选择和后果。

高风险或跨层功能先打通一条最小真实端到端路径：真实输入进入系统，经过核心处理和真实依赖，产生用户可观察的结果。以这条可运行骨架证明方向可行，再逐步补齐其余行为。

实现采用小而完整的变更：每次解决一个可独立说明和验证的问题，相关代码与必要测试一起修改，功能修改与无关重构分开。合适的复杂度由当前已证实需求决定，不为假设中的未来场景增加抽象、配置和兜底。

阅读复杂代码时，当前代码负责人只记录后续定位、实现或验证会用到的入口、主要调用、数据流、相关测试、当前猜测和反例。能够解释目标行为并确定修改位置后停止扩展代码地图；用日志、调试、对照场景或小实验验证修改位置、预期行为和测试含义。

## 委派与连续责任

位置或行为不清楚时，用 `explorer` 回答入口、调用关系、数据流和测试覆盖等边界明确的问题。总体目标、架构边界和验收已经确定，但一个代码目标仍需连续调查、实现、整合和验证时，让 `code-executor` 掌握该目标或模块。方案、接口和验收已经确定的独立实现可以交给 `worker`。

主任务拥有整个任务的总体架构、跨模块技术路线、公共接口和产品行为决定；可以让 `code-executor` 调查候选路线并提出建议，结合其他阶段作出决定后再授权实施。`code-executor` 在已确定的架构边界内自行决定模块内部实现；证据要求改变总体架构、跨模块路线、公共或共享接口、产品行为或任务范围时，交回主任务判断。

`code-executor` 把边界明确的调查、机械实现、独立组件、批量修改，以及步骤和判断标准已经确定的验证交给合适的下级，自己掌握需要连续理解整个模块的技术判断、关键代码、接口整合、复杂失败和最终验收。委派时写清职责或目标文件、接口、必须保留的行为、修改边界和验收命令；每项责任只有一个所有者，已经委派的部分不重复执行，可以继续不重叠的部分，所有剩余责任都已派出时等待报告。

并行工作以文件、接口和责任能够可靠分开为条件；共享同一个文件、接口或状态的工作由一个连续负责人串行处理。`worker` 验证自己负责的执行单元，可以运行局部检查、固定测试或工作量较大但步骤和判断标准明确的验证批次；需要跨组件集成、连续诊断并修改、真实宿主加载或完整用户流程验收时交回 `code-executor` 或主任务。`code-executor` 负责模块内的下级整合、完整测试和复杂失败；主任务根据报告检查会影响总体决定的关键差异，并负责跨阶段或跨目标的最终集成与验收。

## 验证、评审与交付

验证强度由失败代价和改动范围决定：纯逻辑用局部测试，模块交互用集成或契约测试，外部服务、浏览器、数据库和用户关键任务使用真实环境或端到端验收。测试应覆盖当前关键行为、真实故障和高风险边界；修改同一机制时合并或替换已有用例。

评审先看目标和整体设计是否成立，再检查关键调用链、权限与数据边界、失败处理、复杂度和测试是否能在代码出错时真正失败。测试通过只是证据之一；用户要求的真实模型、真实宿主或真实使用路径是完成条件时，以该路径的可观察结果作为最终验收。

发布或交付前确认系统仍可构建、相关测试通过、失败可诊断、必要时可回滚。本次改动影响已有模块说明、架构文档或设计记录时同步更新。交付时说明改了什么、为什么、运行了哪些验证，以及哪些部分仍未验证。成功标准已经满足，而且没有会改变验收结论的失败或未知时结束。

## 停止补丁并返回调查

出现以下信号时，暂停继续叠加修复，回到事实调查和设计阶段：

- 同一故障在修复后再次出现，或连续故障表明它们来自尚未理解的同一机制；
- 新证据推翻了入口、状态、依赖或用户流程的原有假设；
- 测试持续通过，但真实验收路径持续失败；
- 一个局部修复开始影响多个阶段，或错误处理增长快于核心功能；
- 当前负责人无法清楚说明故障的因果链和下一次修改为何能够解决根因。

先补齐事实表、更新流程或状态模型，并用最小实验重新验证最高风险假设。故障造成外部影响、重复返工或暴露流程缺口时，做简短复盘，记录影响、根因、证据和一至三个能够防止复发的改进行动。
