# Code Development

目标是在保持用户已有工作和现有正确行为的前提下，把真实问题转化为经过设计、实现、独立评审和实际验证的可用结果。不同代码任务沿同一条主干推进：

```text
理解问题与工程环境
→ 设计并消除关键未知
→ 小批量实现和真实集成
→ 独立评审与分层验证
→ 交付、观察和迭代
```

主干顺序保持稳定，执行深度随风险和未知变化。明确、低风险的局部修改可以在一次调查、修改和验证中走完。陌生平台、外部依赖、跨模块功能和难以回滚的改动需要明确完成各阶段。流程用于提高正确性，不为通过阶段制造无用文档、测试或仪式。

## 理解问题与工程环境

从用户要获得的结果和可观察验收路径开始，确认修改范围、必须保持的行为和当前事实。以当前代码、配置、测试和实际运行结果为准，沿最相关的入口、调用关系、数据流、依赖和已有实现建立足以支持本次决定的系统模型。区分已经证实的事实、合理推断和会改变路线的未知。

在宿主平台、框架、API 或第三方依赖上开发时，把它们视为工程环境的一部分。需要时核实当前版本的官方文档、源码、示例、发行记录和真实加载行为。不能控制的上游行为不凭记忆假定。已经能够说明代码从哪里进入、怎样与现有系统交互、结果如何观察，而且剩余未知不会改变实现路线时，停止扩展调查。

仍有会推翻总体方案的未知时，继续只读调查或做只回答该问题的最小风险实验。实验结果足以选择路线后进入设计。静态推测、mock 成功和代理指标不能代替任务要求的真实系统证据。

扩大实现、专项研究、独立评审或成套测试前，先确认本次改动经过现有系统的哪个真实入口，以及它将改变哪项用户结果。尚未确认时，继续项目调查或做只回答这个问题的最小验证。

仍有会改变 demo、工作路线或明显投入的核心价值、使用体验、成品形态或验收取舍，而且上级合同和当前项目证据都没有给出答案时，当前代码阶段不通过实现猜测用户偏好，把具体差异、已有证据和实际影响交回上级。

安全、权限和边界问题由当前代码、即将执行的具体行动或合同要求触发。没有实际触发依据的风险保留为待验证假设，不把它扩展成专项架构、研究或验证，也不用它替代对现有系统的理解。

## 证明路线，而不是维护路线

把用户问题、可观察结果与当前实现路线分开。框架、架构、库和工具是待验证的解决假设。除非用户或既有系统明确要求，不因已经写了代码或解决了若干路线内问题而变成必须保持的目标。新问题出现时，先判断它是目标本身需要完成的工作、可行路线内的普通缺陷、证据缺口，还是当前路线制造的结构性负担。

跨层、陌生、高成本、批量或难以回滚的路线在扩大实现前，先找出最可能否定它的用户结果，并用最小真实切片验证。最小端到端路径只证明入口和数据链能够连通，不自动证明产品方向成立。例如桌面界面的窗口启动不能代替代表性截图、交互、刷新和资源体验。语义迁移的事务成功不能代替高风险内容样本和真实检索或使用效果。样本按本任务风险选择，不把这些例子机械套到无关任务。

路线能够运行也可能已经失效。过程指标通过而代表性用户结果失败或长期未知、同一路线反复要求跨组件补偿或重建成熟平台已有能力，或者剩余工作的主体已变成维护路线自身且成本相对成熟替代明显失衡时，停止扩大投入。先做一个能区分局部缺陷与结构错配的最小实验。证据足够后按用户结果、剩余成本、风险、验证路径、可复用资产和切换代价比较继续、缩小或换路。既有投入是沉没成本，不作为继续理由，已经可靠工作的可复用部分单独保留。

路线仍有会改变方向的未知时，优先采用连续的小步试探，不把完整实现当作第一次实验。每一步应当小而真实、容易观察和尽可能可撤销，专门减少一个会改变路线的未知。开始前明确本步要回答的问题、使用的真实路径或代表性数据、支持继续与触发调整的判据，以及它与最终系统仍有什么差异。取得反馈后更新当前模型，再决定扩大、调整、补证据或换路。小步按决策信息划分，不按文件或命令机械切碎，也不要求把每次试探都变成对用户的进度汇报。路线和验收已经清楚的普通局部工作可以直接完成，不为形式增加试探。

## 先交付最小核心成品

对于陌生、跨层、高成本、依赖真实宿主或外部服务，或者已经出现代表性结果不推进的路线，第一次实现先交付一个最小核心成品，也就是 demo。它保留用户需求中不能缺少的核心价值，让与风险相称的代表性输入、状态或工作负载通过实际入口、核心处理、必要状态和真实依赖，产生用户可以直接判断的结果。只完成接线、框架、局部算法、测试或过程日志的技术骨架不是 demo；避开核心问题的玩具样例也不是 demo。

Demo 用于尽早判断路线是否值得扩大，不是把当前路线修到成功的义务。Demo 第一次失败后，先定位首个阻碍，并只做一个能区分局部缺陷与路线问题的最小修复或实验。这个实验没有推进核心结果或原因判断，或者同一路线为了通过 demo 不断增加前提、例外和跨组件补偿时，比较缩小、替换或重做路线，不再沿原路线补丁，也不扩展外围功能、参数组合、兼容层和成套测试。Demo 成立后，只有合同已有明确验收标准和连续推进授权时，当前代码阶段才直接扩展完整行为、边界、体验、规模和高风险验证；否则把用户可以判断的结果、差异和剩余投入交回上级校准。

为 demo 选择可比较、可归因的验收单位，而不是强求单个固定且完全可重置的样本。确定性行为可以使用可重放的隔离样本；随机性、并发时序、统计噪声、不可逆状态或受限外部服务则使用与故障模型相称的受控工作负载、状态和版本记录、隔离环境、观测计划与判据，并说明这些证据和真实条件的差异。解释结果前核实实际加载的工作目录或提交、未提交差异、持久化配置、构建产物、服务实例和外部依赖；结果不能归因于当前修改时，先修正环境。

确定性流程按实际路径定位第一项错误转换。并发、性能或概率行为按预先声明的观测单位、覆盖窗口、不变量或阈值定位，不把单次轨迹当成结构性故障。每项实验减少一个会改变路线的未知，并让结果能够归因于明确假设；统计重复或参数搜索按预先定义的实验设计推进，不连续猜数字。验收工具覆盖成功、明确失败、无变化、跳过或其他合法终态，不能把合法终态误判为无限等待。

完成约定的观测计划后核心结果仍未成立，下一项动作已不能减少关键未知，或者跨组件补偿增长快于用户价值时，停止当前执行循环。昂贵调用本身不是停止理由；再次执行前先说明它要回答的验证问题、观测计划和判据，计划内重复属于同一实验。停止时区分已经成立的代码与测试证据、仍未成立的核心结果、尚未减少的未知和路线假设，回到工程环境、设计或路线选择；需要改变跨模块路线、成品形态或明显增加投入时沿责任链交回决定。

普通局部修复只有在入口、验收方式和影响边界已经明确，而且不存在会改变路线的状态、并发或外部依赖未知时，才不触发整套阶段门，可以按相应风险直接修改并验证。

## 设计并消除关键未知

解释当前行为、目标行为及二者之间的差异，确定主要组件、接口、状态或数据路径。重大、跨层或长期影响明显的改动在编码前形成并评审简短设计，说明目标、实现策略、关键取舍和验收。局部改动用清楚的变更说明即可。设计应让没有参与当前推理的工程师能够判断整体方向是否成立。

实现界面、文档、通知或其他用户可见内容前，区分必须准确保留的事实、名称和用户文字，与只用于指导实现的目标、理由、例子、限制和验收解释。后者应体现在结构、行为与验证中，不能因为出现在需求、合同或注释里就原样成为成品文案。完成后从不了解任务提示的首次使用者角度检查每段可见文字。不能帮助其识别状态、作出判断或采取行动的自我解释，应删除或移到开发与交付说明。

设计评审发生在大量代码写下之前。先判断改动本身是否合理、是否属于当前系统、依赖假设是否成立，以及主要结构能否满足用户目标。根本问题没有解决时，不进入实现细节。

高风险或跨层功能可以先打通最小真实端到端路径，让真实输入经过核心处理和真实依赖，产生可观察结果。它用于证明入口和数据流，也是第一个实现切片，但只有切片同时覆盖最可能否定路线的用户结果时，才能支持架构方向。它始终不是成品质量标准。方向成立后仍要补全用户真正需要的行为、边界和体验。

## 小批量实现和真实集成

把设计拆成小而完整的变更。路线不确定时，先做能取得方向反馈的最小变更，证据支持后再逐步扩大。路线明确后，每个变更只解决一个可独立理解和验证的行为，相关生产代码、测试和必要说明一起完成，合入后系统仍然可用。按行为和集成边界拆分，不按文件数量或执行者拆分。增加接口时同时给出真实用法，功能修改与无关重构分开。

每完成一个关键切片就构建、集成并取得与该层相称的反馈。插件、Mod、浏览器、数据库或外部服务相关行为，应尽早在真实宿主或真实依赖中验证入口和主要链路。不要等全部代码写完后才第一次运行真实路径。普通局部失败由当前负责人在同一切片内修正，证据推翻设计时返回上一阶段。

实现复杂度以当前已证实需求为准。先查找能够可靠复用或借鉴的成熟方案，包括开源实现、项目已有实现、平台能力、标准库、已有依赖、同类系统和当前技术出现前的成熟做法。现成方案不需要能够整套照搬。它的架构、算法、接口、数据路径、工作流程、失败经验和适用边界也可以提供实现方法。判断哪些部分适用于当前项目，再选择直接采用、局部调整、组合其思路，或据此编写满足当前结果的最小新实现。一次性操作直接写在使用处，几行相似代码通常比提前创建 helper、utility 或抽象层更合适。不为假设中的未来需求增加配置和兜底。

用户需求、阶段合同和项目权威资料已经对齐时，以它们形成唯一实现。把权威主路径失败、缺失或不确定时改走另一来源并继续产生结果的实现视为兜底。只有合同要求或已经观察到的系统边界失败需要恢复，并且触发条件、结果语义和验证方式明确时，才增加或保留这类路径。

依赖内部代码和框架已经提供的保证，不重复实现同一机制。能直接修改代码时，直接完成改动并删除被当前合同取代的路径。新证据与合同冲突时交回具体矛盾，由上级决定是否改变合同。当前合同要求的信任边界、安全、数据保护、兼容性和可访问性继续保留。

修改只覆盖完成当前结果所需的代码。修复缺陷不顺手清理周边代码，简单功能保持简单，未修改的代码不补文档字符串、类型注解或解释性注释。逻辑确实不直观时写必要注释。确认不再使用的代码直接删除，不留下重新导出、变量改名或 `// removed` 一类兼容痕迹。

## 保持项目可接续

每个代码阶段交付前，判断未来正确修改是否依赖无法从代码和测试恢复的稳定信息。非显然的架构决定、外部约束、权威来源、跨组件不变量、容易被重新采用的否决路线，以及特殊的构建、迁移或运行前提，应当更新到项目已有的权威资料。项目没有合适入口时，用简洁 `AGENTS.md` 索引详细设计资料。

资料记录当前仍有效的背景、决定和理由、代码入口与数据流、验证方法、已否决路线及重新判断条件。对话流水、临时故障、命令日志和模型工作痕迹留在任务记录中。代码和测试已经清楚表达的普通实现不重复写入资料。文档必须与最终成品一致，不能把候选、计划或半成品写成当前设计。普通、局部且可以从代码和测试完整理解的改动不为形式新增文档。

## 独立代码评审

独立评审用于实质降低误交付风险或补足实现者视角。功能行为、接口、状态或系统结构发生非机械变化时，默认考虑在实现者完成自查后交给干净上下文的 `code-reviewer`。局部、影响边界清楚、结果唯一且已有充分证据的修改可以由当前负责人复核。即使修改本身是机械性的，范围大、跨组件、难以回滚或真实验证不足时，也应进行独立评审。

需要评审时，阶段负责人提交完整的评审合同，其中包括准确的基线和候选、用户或阶段需要得到的可观察结果、已接受的设计或约束、实际 diff 或变更文件，以及已经取得的测试和运行证据。会决定结论的项目规则、接口或设计记录应当给出准确入口。评审合同不提供期望结论，也不提示 reviewer 寻找某个预设问题。

评审从整体开始：改动是否应该存在，设计和系统集成是否成立，用户与调用者得到的行为是否正确。然后检查关键调用链、状态和数据边界、依赖与兼容性、失败处理、复杂度、可维护性和测试有效性，最后逐行理解被分配的人工编写代码。技术事实、项目规范和可复现证据高于个人偏好。不因纯风格意见阻塞交付，也不因代码能运行就接受降低整体代码健康的改动。

`code-reviewer` 只读给出“可合入”“要求修改”或“证据不足”的评审结论，并报告按严重程度排序的可操作发现。发现定位到准确文件和最小行范围，说明触发条件、影响和需要纠正的机制。没有阻塞问题时仍说明决定结论的证据、残余风险和未验证路径。

“要求修改”时，实现负责人修复问题，或者用技术事实和可复现证据反驳发现；可能使原结论失效的变化完成后重新评审受影响范围。“证据不足”时补充缺少的合同、代码范围或验证证据，不把它当作通过。未经修复、证据反驳或上级明确改变合同的阻塞问题不能被静默忽略。发现推翻设计或工程环境假设时返回对应阶段，不在错误结构上继续补丁。

实现工作已经属于阶段负责人时，由该负责人组织评审、接收报告、安排返工并重新验证。上级不为同一阶段逐项管理评审和返工，只接收阶段负责人整合后的结果或需要跨阶段决定的问题。

## 分层验证与持续集成

测试与实现同行，用于证明用户要求的行为并保护后续修改。测试范围以足够支持交付判断为准，围绕用户要求的行为和错误代价高的边界设计。根据故障层次选择证据：纯逻辑使用局部测试，组件边界使用集成或契约测试，完整产品行为使用系统测试、端到端流程或真实宿主验收。

测试本身也要接受评审，确认实现发生目标错误时它确实会失败。修改同一机制时优先更新或合并已有用例，不为增加测试数量重复覆盖同一判断。测试预期与用户结果、真实接口或正确设计冲突时，修正测试或重新判断设计，不为通过测试而扭曲生产代码。

每个小变更在提交前运行相关检查，进入共享主线后持续构建和测试。失败时修复或回退，不把错误留给后续集成。测试通过只是证据之一。用户要求的真实模型、宿主、外部服务或使用流程是完成条件时，以该路径的可观察结果作为最终验收。

## 交付、观察和迭代

交付前确认实际产物能够构建或加载，相关检查通过，失败可诊断，并在风险需要时具备回滚或恢复办法。影响现有接口、使用方式、构建、测试或发布流程时同步更新相应文档。

能够分阶段发布的系统先在有限环境或用户范围中观察，再扩大影响。本地插件和 Mod 使用测试配置、测试存档或独立实例取得同类证据。交付时说明改了什么、实际运行了哪些验证、观察到了哪一层结果，以及哪些真实环境或用户路径仍未验证。成功标准已经满足，而且没有会改变验收结论的未知时结束。

## 停止补丁并返回上游

同一问题修复后再次出现、新证据推翻入口或状态假设、测试持续通过而真实用户结果持续失败、局部修复开始跨越多个阶段、路线补偿工作增长快于用户价值，或者负责人已经无法解释故障因果链时，停止叠加修复。先用最小真实实验区分普通缺陷与路线错配。普通缺陷由当前负责人继续处理，路线假设受到实质反证时回到工程环境或设计阶段，更新当前模型并重新确定路线。
