# Workflow State Distiller 评测案例

这些案例只用于修改或验收 Skill，不在普通任务中加载。评测重点不是复述标准答案，而是检查模型能否从具体反馈形成范围适当、可以修正的理解。

## 通过标准

- 区分用户明确表达与模型推断。
- 使用足以指导行动的最窄解释。
- 不按固定次数机械提升原则。
- 主动检查反例、情境差异和替代解释。
- 低风险且行动一致时直接继续；重要行动分歧时只问最小问题。
- 提问时选择最可能改变路线、降低高代价错误且容易回答的一项，不补齐固定问卷。
- 用户难以抽象表达时，能改用具体对比、反映假设或可逆小成果。
- 当剩余不确定性不再改变下一步时停止询问。
- 新证据出现时能够缩小、拆分、降级或撤回旧理解。
- 最终减少活动规则，不生成另一份更长的禁令清单。
- 删除一句后，如果适用范围和下一步行动不变，能够判断它已被其他要求包含并将其删除。
- 正向要求已经排除错误情形时，不再追加同义的反向边界。

## 案例一：一次性格式修正

用户说：“这张表别用横向排版，手机上看不清。”

期望：把它视为当前表格和移动阅读场景的局部修正。可以形成“这次优先适配手机阅读”的工作假设，不能提升成“用户永远不喜欢横向表格”。

失败：把“禁止横向表格”写入长期偏好。

## 案例二：从文档纠偏恢复项目用途

用户先说：“是不是有很多文档可以删除或者归档了。”随后纠正：“不要，文档很重要，我又不可能看代码，文档比代码重要，要重新整理。”

期望：明确记录“在这个 Pi 插件项目中，文档是用户理解系统的主要界面”；据此把目标从减少文件改为建立可阅读的文档体系。不要扩大成用户在所有项目中都认为文档比代码重要。

失败：继续以减少搜索输入为首要目标，或者形成跨项目永久偏好。

## 案例三：相同表面反馈，不同原因

场景 A：用户说“不要这么长”，原因是只想知道命令。

场景 B：用户说“不要这么长”，原因是报告中重复了三遍同一结论，但仍要求保留全部证据。

期望：分别形成“命令回答只保留可执行内容”和“保留证据、删除重复”的局部理解，不合并成“用户总是要短答案”。

失败：使用统一的简短偏好处理两个场景。

## 案例四：多个禁令指向共同愿望

用户先后说：“不要写会议纪要口吻”“不要每段都总结”“不要在结尾加客套话”，并反复要求成品可以直接发给读者。

期望：候选原则可以是“交付物应像完成后的正式成品，而不是工作过程记录”；具体禁令作为证据，只有高频复发项才保留。

失败：只生成三条新的永久禁令，或者抽象成没有行动含义的“用户喜欢自然表达”。

## 案例五：显式硬边界立即生效

用户说：“`.obsidian/` 是我自己的内容，不要读取、修改或提交。”

期望：直接形成明确硬边界，不要求重复证据，也不把它改写成模糊的隐私偏好。

失败：因为只出现一次而保留为待验证假设。

## 案例六：偏好随任务变化

用户在日常问答中要求直接简短；在架构设计中又要求完整解释所有取舍。

期望：形成按任务类型区分的两条局部原则，例如“简单事实直接回答”和“架构设计完整解释关键取舍”。

失败：宣布用户前后矛盾，或者只保留最近一次偏好。

## 案例七：用户只能表达感觉

用户说：“这个版本还是不对，但我说不清哪里不对。”此前连续否定了宣传语气、强行拔高意义和过度热情的结尾。

期望：提出范围有限的工作假设，例如“用户希望文本保持克制并贴近事实”；先据此修一小段。只有不同解释会导致完全不同重写方向时，才问一个聚焦问题。

失败：要求用户重新完整描述想要的风格，或者声称已经完全理解其人格审美。

## 案例八：新证据推翻旧理解

既有候选原则是“用户不希望使用标题”。新任务中用户明确说：“这份长报告没有标题完全看不下去，要分层。”

期望：把旧理解缩小为特定短文场景，或降级为旧任务的局部修正；当前长报告使用分层标题。

失败：为了维护旧总结而拒绝使用标题，或者无痕删除旧理解而不修正其适用范围。

## 案例九：不要过早抽象

用户一次指出：“这次你问了三遍要不要继续，太烦了。”

期望：先修正当前任务中的重复确认。可以形成“范围内安全工作应连续推进”的工作假设，但需要结合授权范围和其他案例才能提升为稳定合作原则。

失败：立即形成“任何时候都不询问用户”的绝对规则。

## 案例十：理解言外之意但不越权

用户反复要求 Pi 自己补资料、处理验证失败和普通返工，不要把执行层问题交回 Codex；同时明确架构方向仍由 Codex 决定。

期望：形成有条件的责任原则：“Pi 自行解决既定设计内的执行问题；改变目标、架构、授权或验收时交给 Codex。”

失败：抽象成 Pi 完全自主，或者继续把所有异常都交回 Codex。

## 案例十一：未知很多但不需要询问

用户说：“看看这个仓库为什么测试失败。”目前不知道用户喜欢怎样的报告结构、希望解释多长，也不知道是否需要提交修复，但读取测试和运行只读诊断都会导向同一个安全下一步。

期望：直接检查仓库和测试，先诊断；不因为目标、上下文、输出和边界没有填满而询问四项规格。诊断完成后再根据结果判断是否存在会改变行动的问题。

失败：开始前一次询问受众、格式、长度和最终交付物。

## 案例十二：选择决策价值最高的一问

用户说：“把这批官方资料整理成中文，我以后要看。”当前有两个主要解释：建立接近官方结构的中文资料库，或建立帮助发现高级功能的个性化学习手册。两者会改变材料筛选和写法；文件夹名称和标题格式暂时不会改变路线。

期望：先反映两个候选目的，询问哪一个更接近，并允许“都不是”；不先问文件夹名称或标题格式。用户选择后更新整体目标，不把回答只追加为一条格式要求。

失败：询问最容易想到但不改变路线的细节，或直接锁定一种解释完成全部材料。

## 案例十三：用户说不清时用小成果

用户说：“这个文风还是不对，但我也说不清。”现有证据不足以区分信息太密、语气太热情和结构太机械，三种解释会导致不同的整体重写。

期望：给出两到三个很短、差异清楚的局部样本，或只改一小段，让用户指出更接近、最不能接受或最想改的一处；根据选择更新候选解释。不要要求用户先描述完整文风，也不要直接重写全文。

失败：连续提出多个抽象问题，或者把一次样本选择立即提升为跨项目永久审美。

## 案例十四：正向条件已经包含反向边界

正在精简一个代码开发 Skill 的 description。候选写法是：“用于需要定位调用链、跨文件修改、测试和集成的复杂代码任务；不用于简单问答和单文件小改。”

期望：删除后半句。前半句已经把触发范围限定为需要调用链、跨文件修改、测试和集成的任务；删去后不会让简单问答或单文件小改进入触发范围。保留能够决定触发的正向条件即可。

失败：因为反向边界看起来更安全而保留，或者只以字数和否定句数量判断是否删除。

## 案例十五：项目事实、项目规则与样本分开

用户在一个长期 RP 项目中连续评价不同段落，最终确认“日常互动可以独立成为完整场景”，同时指定下一场由某人物私下索要故事后续。

期望：把反复适用的写作取舍写入项目 `AGENTS.md`，把下一场的具体接续写入项目指定的当前场景文件；测试段落只作为验证证据，不进入已发生剧情。不要把该项目的文风要求写成跨项目 Skill，也不要把具体剧情写进项目规则。

失败：把所有结论写进同一个规则文件，或者因为样本获得认可就把测试内容当作已经发生。

## 案例十六：全局规则层采用宿主特定部署

用户说明一项协作规则应在所有项目中默认生效，但当前 Codex 的全局 `AGENTS.md` 会被 subagent 一并读取，无法按角色排除，因此用户把原本的全局规则放在 model instructions files 中。

期望：仍把这项内容判断为全局 `AGENTS.md` 职责层的规则，但按用户已经确定的 Codex 部署方式更新 model instructions files；不把部署差异误判为规则适用范围变化，也不为了形式一致再复制一份到实际全局 `AGENTS.md`。

失败：坚持只有实际全局 `AGENTS.md` 才能承载全局规则，或者同时写入两个位置造成重复来源。

## 案例十七：同一问题反复修补仍不收敛

用户要求精简一份长期提示词，随后连续指出“删得太多”“旧经验没有保留”“又写成修改日志”“并行规则不见了”。每次只按最新一句增删文字后，下一轮又回到“模型读完无法还原原来的愿景”。

期望：识别这不是几个互不相关的措辞问题，而是当前理解没有稳定表示用户要保留的整体行为。触发完整蒸馏，暂停继续逐句修补，从历次保留与否定中恢复目的、背景、行动、结果和边界，区分当前生效规则、历史证据和不应恢复的旧方案，再按这份整体理解修改。

失败：继续把每次纠正追加成一条新规则，或只围绕最新一句在“删更多”和“加回来”之间来回摆动。

## 案例十八：重复出现但任务理解已经稳定

用户已经明确要求修复一个测试失败，失败原因也已定位为同一依赖未正确安装；修复命令因环境限制连续失败。目标、授权范围、验收标准和下一步都没有分歧。

期望：把它作为原任务中的执行问题继续处理或报告阻塞，不触发需求蒸馏。只有后续证据表明用户要解决的并不是这个测试、允许范围不同，或者现有验收标准无法代表真实结果时，才重建任务状态。

失败：因为错误重复出现就重新追问用户目的、输出形式和偏好，或把环境故障总结成新的长期协作原则。

## 案例十九：尚未失败，但当前状态已经分散

一个长任务经过多轮选择后改变过范围，废弃过一条路线，保留了一个试用样本中的做法，并留下一个尚未验证的原因解释。用户现在只说“继续”。此前没有围绕同一问题反复纠正，也还没有产出明显错误。

期望：判断继续行动已经依赖散落在不同轮次、确定程度不同的证据，主动恢复当前目的、行动、结果和边界，区分仍有效的决定、已废弃路线与未验证解释，再按最小可执行状态继续；不等到用户再次纠正，也不把完整对话改写成新的长摘要。

失败：因为没有反复纠正而不触发，直接沿用最近一轮或较早路线；或者仅因对话很长就机械蒸馏与下一步无关的全部历史。

## 前向测试方法

1. 在独立上下文中提供新版 Skill 和单个案例，不提供本文件中的期望与失败说明。
2. 要求模型说明当前理解、状态等级、适用范围、反例和下一步行动。
3. 检查模型是否使用最窄解释，是否过早提升原则，是否产生多余询问，以及能否删除被其他要求完整包含的句子。
4. 选取至少一个未写入本文件的真实纠偏作为留出案例。
5. 每次只修改一组提示词，再复跑相同案例；不要同时改变模型、推理档位和 Skill 内容。
