# Workflow State Distiller

## 目标

从用户明确说过的话、实际选择、纠正和试用结果中，逐步弄清当前任务要做到什么、结果拿来做什么、哪些代价不能接受，以及用户希望怎样协作。

用户无需在项目开始时一次说清完整规格。从已经明确的部分开始，把当前理解作为可修正状态。新证据出现时更新、缩小、拆分或撤回旧理解。

成功意味着 Codex 下一步做得更接近用户的实际需要，几条相关反馈被合并成更少、更清楚的要求，而且能看出哪些是用户明确说的、哪些是暂时推测的、哪些还没有确定。

当前任务里的反馈先只用于当前任务。只有用户明确确认，或者多个项目中的实际选择都支持同一要求时，才把它当成跨项目原则。

## 加载后的范围判断

先判断是否需要完整重建任务状态。若继续行动可能因为零散或失效的理解而遗漏有效要求、误判适用范围或改变下一步，就执行本 Skill。若目的、边界和下一步仍然稳定，就按原任务继续，不因信息很多、执行错误、普通返工或等待外部状态而机械蒸馏。

需要完整重建时，先暂停依赖旧理解继续扩写规则或大幅重做成果。不要只总结用户最新一句话，而要恢复目的、背景、行动、结果、边界及仍未证实的原因解释之间的当前关系，形成足以解释保留、否定和变化的最小整体理解后，再继续行动。

## 维护的任务状态

只维护会改变行动的五类内容：

- **目的**：为什么做、最终要保护什么，以及发生取舍时优先什么。
- **背景**：交付对象、使用场景、关键来源、实际选择、实验结果和仍影响判断的失败路线。
- **行动**：Codex 当前要做什么，以及确实会改变结果的协作方式、方法或顺序。
- **结果**：交付物、受众、完成状态、详细程度和使用方式。
- **边界**：必须保持不变的事项、权限范围、不可接受的代价和需要确认的决定。

这些内容可以暂时不完整。提问是形成和修正理解的正常方式。答案可能改变目标、结果、边界、重要路线或高成本行动时，优先把相应问题问清。能够从任务对象查明的信息主动调查，不依赖回答的工作可以继续推进。记录一项理解时，同时记清它来自哪里、只适用于什么情境，以及什么新证据会让它失效。

回看历史时，只看可能改变当前决定的材料。已经不影响行动的旧对话和调试过程留在原始记录里。

四类证据必须分开：

1. **直接证据**：用户的选择、保留、否定、实际使用感受和已经发生的结果。
2. **明确决定**：用户直接确认的目标、限制、权限和取舍。
3. **原因假设**：用户或模型对“为什么”的解释，分别标明来源。
4. **未形成偏好**：现在没有答案，需要通过比较或试用形成。

用户的直接感受可以确定“结果不符合需要”，但不能单独证明原因。明确提出的原因仍先作为原因假设，除非有独立证据或后续选择支持。

## 这些理解有多确定

根据证据强度区分：

- **明确事实**：用户直接说明的目标、决定或限制。
- **局部修正**：只对当前内容、版本、场景或动作生效。
- **工作假设**：目前最合理、可以指导低风险行动，但以后可能改掉的理解。
- **候选原则**：几个不同情境都支持，但适用范围或例外还不够清楚。
- **已确认原则**：用户明确认可，或者已有稳定证据、清楚范围，并且能正确判断相似场景中的选择。
- **硬边界**：用户明确要求不能越过，或涉及安全、权限和不可逆影响的限制。

工作假设和候选原则只用于它们有证据支持的范围。长期资料只记录已确认原则和硬边界。

一项理解是否升级为原则，要看它有没有不同来源的证据、范围是否清楚，以及它能不能正确解释相似场景中的选择，不能只数出现了几次。新证据也可以缩小、替换或取消已经确认的原则。用户明确提出的硬边界立即生效，不需要反复证明。

## 要求写多重

规则的措辞要和证据强弱相称：

- 局部修正写成“这次……”。
- 工作假设写成“目前先按……处理”。
- 候选原则写成“在这类情境中通常……”或“优先……”。
- 已确认原则写成清楚的默认要求。
- “必须”“不得”“绝不”“任何时候都”等最强措辞只用于用户明确要求的硬边界，或安全、权限和不可逆风险。

正向要求也可能写得过强。证据只支持“优先简洁”时，就保持“优先”，不要改成“所有回答必须极短”。

## 蒸馏流程

### 1. 先弄清反馈发生在哪

确定当时的任务、交付对象、Codex 的行动、用户实际否定或保留的内容，以及反馈改变的是结果、用途、取舍、合作方式还是局部细节。

### 2. 把事实和推测分开

先记用户原意、实际选择、试用结果和已经发生的事实，再说明 Codex 怎样理解。说明这项理解只适用于哪里，并允许后续证据改掉它。

### 3. 用下一步行动检验理解

先保留足以决定下一步的理解：用户想要什么结果、不接受什么代价、这项取舍适用于哪里。然后逐项删除。如果删除某项后，目标、输出、提问、权限、风险处理和下一步行动都不变，该项不进入当前状态。有多个解释时，只保留会导向不同重要行动的解释。导向同一安全行动的差异不需要记录。

### 4. 检查还有没有别的解释

检查有没有相反证据，或者同一句反馈是否可能出于别的原因。如果一项理解只能解释这一次反馈，还不能判断相似场景中的选择，就继续把它当作工作假设。出现反例时，缩小适用范围、拆成有条件的要求，或者降低确定程度。

### 5. 决定继续做、先给样本还是提问

判断哪一步最值得做：

- 不同解释仍导向同一个安全行动时，采用最窄工作假设继续。
- 可逆的小成果更容易暴露偏好时，先交付一个局部样本或修改。
- 不同答案会改变目标、重要结构、权限、不可逆操作或用户可见结果时，提出一个最有价值的问题。
- 涉及安全、权限和高代价后果时，先确认相应边界。
- 用户已经明确说明目的时，直接更新状态并继续。

选择问题时，同时考虑答案会怎样改变下一步、能够避免多大的错误，以及用户回答要花多少时间和注意力。可以询问具体事件、给出清楚的对比、请用户指出当前理解哪里错了、确认硬边界，或让用户评价一个小成果。理解仍然开放时，让用户自由表达。开放表达告一段落并已经形成可以直接比较的选择时，可以建议使用 Plan mode 降低回答负担。默认一次先问最有价值的一项。问题已经不会改变下一步，或者提问带来的负担大于可能减少的错误时，继续执行。

### 6. 根据新回答更新整体理解

收到回答、拒绝、选择或成果修改后，重新检查相关目的、背景、行动、结果和边界。调整暂时理解的确定程度，删除依赖旧理解的要求，并判断这只是局部修改，还是已经换了一条路线。

同一目标内的长度、措辞、信息密度和局部格式通常采用小步校准。用途、成功标准、交付对象或问题定义变化时，重建相应任务状态。

## 从“不要这样”弄清“应该怎样”

用户提出否定或禁令时，依次恢复：

1. 用户希望保留的结果。
2. 这次反馈拒绝的失真、风险、冗余、打扰或成本。
3. 反馈适用的对象和情境。
4. 能直接指导这次以及类似选择的正向要求。

如果问题只是 Codex 自己多加了内容，先删掉并改好当前成果。只有这次纠正还会影响类似任务，才继续总结成规则。候选要求形成后逐句做删除测试：删去一句后，如果适用范围、下一步、提问、权限和风险处理都不变，这句已被其他要求包含，不进入当前状态。反向边界只在删去后会重新包含某种具体错误情形，而且该错误容易复发或风险较高时保留。硬边界按用户原意保存。

## 失败与探索历程

失败只有在它改变了目标、路线、边界、验证方法，或者能防止以后重复走错路时，才放进当前任务状态。记录时只写“原来怎样判断—什么证据推翻或修正了它—现在有什么影响”。已经解决且不再限制后续行动的报错、尝试过程和实现细节，从当前要求中删除。

出现多条分支、回退、吸收或废弃路线时，使用 `workflow-route-mapper` 保存完整路线图。本 Skill 只从路线证据中维护当前有效状态。两者同时需要时，先由当前任务责任人用本 Skill 确定当前有效状态和改变路线的证据，再让 `workflow-route-mapper` 据此更新路线图。路线图随后作为新证据返回当前任务责任人，不代替当前状态，也不再次触发一轮相互转交。

## 当前状态的维护

每项当前要求只保留一次。新结论替代旧结论时，保留当前结论及理解修正所必需的原因。旧例子只在仍能作为证据或反例时存在。当前状态可以采用以下最小结构，并省略空字段：

```markdown
# 当前理解

## 目的
## 背景
## 行动
## 结果
## 边界
## 当前不确定性与下一步
```

明确内容、工作假设和待确认内容在文字中自然标明。完整探索历史留在路线图和证据文档，当前状态保持可直接执行。

## 决定理解保存在哪里

蒸馏首先用于修正当前任务，不自动产生长期文件。用户要求保存，或者已确认理解需要在以后继续生效时，再根据适用范围和用途选择唯一的主要来源：

- 只影响这次工作的局部理解留在当前任务状态。
- 人物、剧情、产品状态等关于项目对象的事实进入项目已有的状态或设定资料。
- 同一项目中反复执行的工作取舍进入项目规则。
- 跨项目但只在特定类型任务中触发的方法进入相应 Skill。
- 所有任务默认遵循的长期要求属于全局规则职责层。
- 样本、试验和失败记录保留为校准或证据，不能仅因结果获得认可就升格为事实或规则。

实际文件位置服从项目约定和宿主机制。部署位置与规则职责不同时，记录并遵循已经确定的部署方式，不把同一内容复制到多个位置。用户没有要求长期化、项目也没有既有资料承载时，先保留在当前任务，不擅自新建长期文件。

## 对用户的输出

- 局部纠偏：简短说明修正后的理解，然后继续任务。
- 用户询问真实目的：说明明确事实、当前最小解释、仍会改变行动的不确定性。
- 用户要求整理状态：输出精简的当前状态。
- 用户要求写入长期规则：只写已确认原则和必要硬边界。
- 已有安全修正方向：先修正成果，让实际选择继续校准理解。

内部分类和候选解释只展示对用户判断当前任务有帮助的部分。

## 验收

- 当前理解能够解释用户的实际取舍并指导下一步。
- 使用了与证据相符的最窄范围和理解强度。
- 规则的措辞力度与证据和风险相称，正向要求没有被写成过强命令。
- 使用清楚、直接的普通中文，读者能看懂对象、动作、适用范围和力度。
- 事实、推断、硬边界和待确认内容保持可区分。
- 反例能够缩小或撤回旧理解。
- 每项当前要求都会改变适用范围、下一步、提问、权限或风险处理。被其他要求包含的句子已经删除。
- 提问能够帮助形成或修正理解，问题的价值与用户负担相称。
- 下一步已经明确且可以直接执行。

维护或重写本 skill 时，读取 `references/eval-cases.md`，先确认旧要求怎样影响行动，再用应该触发、容易混淆和不应触发的案例做前向测试。逐句执行删除测试，并比较理解范围、规则力度、下一步行动和是否提问。不能用文件更短或否定句更少代替语义验收。普通任务不读取该文件。
