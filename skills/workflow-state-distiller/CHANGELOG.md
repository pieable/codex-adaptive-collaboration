# Workflow State Distiller 演变记录

这份记录用于保存 `workflow-state-distiller` 为什么形成现在的结构，以及历次修改想解决什么问题。当前生效规则仍以 `SKILL.md`、`agents/openai.yaml` 和 `references/eval-cases.md` 为准；精确旧文本由只读备份与原始会话承担。

## 始终一致的最终愿景

用户不必在任务开始时一次说清完整规格。Codex 应当从用户明确表达、实际选择、纠正、试用结果和失败路线中，逐步维护会改变行动的目标、上下文、输出形态和边界，并随着新证据缩小、拆分、提升或撤回旧理解。

蒸馏的目的不是替用户猜出一套隐藏人格，也不是把每次不满意写成新的禁令。它应把多条相关反馈合并成更少、更能指导下一步的理解，同时区分用户明确决定、已经发生的事实、暂时原因假设和尚未形成的偏好。明确指令决定交付结果和权限；隐含目标只能在有证据的范围内帮助选择路线、信息密度、主动程度和验证方式，不能自行扩大授权或推翻用户明确保留的内容。

当不同解释仍会导向同一个安全行动时，Codex 应采用最窄工作假设继续；可逆的小成果更容易形成偏好时，先给样本；只有答案会改变重要行动、权限、不可逆影响或用户可见结果时，才提出一个高价值问题。当前可执行状态与完整探索历史分开：当前状态只保留仍会改变行动的内容，路线演变交给原始会话或 `workflow-route-mapper`。

一项理解得到确认后，还要判断它应留在当前任务、项目事实或状态、项目规则、跨项目 Skill 还是全局规则层。保存位置取决于适用范围和用途，不取决于某个宿主恰好使用什么文件名；同一事实或规则应有一个主要来源，用户没有要求形成长期资料时不擅自写入。

## 阶段一：从不断增加禁令，转为恢复用户目的和动态状态（2026-05-30）

- **目标：** 解决 Codex 把每次纠正都变成一条局部禁令，最终规则越来越多、仍然偏离用户真实用途的问题。
- **原有状态：** 助手倾向于逐条执行“不要这样”，也曾把一次具体案例抽象成针对性的规则；对“简要工作流程”的理解一度接近固定行数压缩。
- **问题或新证据：** 用户明确要求不要为了迎合最新纠正不断增加“禁止某事”，而要恢复这些反馈共同保护的目的。用户还补充：格式、语气、结构、粒度和交付形态等多次局部调整，也可能是在逐步表达偏好；“简要”表示删除无关日志，不表示切断重要因果。
- **形成的理解：** 应维护一份滚动的任务状态，记录用户目的、当前工作流、活动原则、硬边界、重复偏好信号和验收标准。具体纠正首先是当前任务证据，只有出现稳定模式后才提炼为更一般的原则。
- **实际修改：** 创建 `workflow-state-distiller` 及 `agents/openai.yaml`；触发范围从反复禁令扩大到多次非主体局部调整；加入用户目的、工作流历史、活动原则、硬边界、废弃规则和验收标准等状态要素。
- **保留边界：** 重要因果历史不能为了“简短”被压掉；具体例子只用于校准，不成为通用规则本身。
- **否决或缩小的路线：** 放弃针对“给老板的成品不要日志”等单一案例设计 Skill；放弃把每次微调直接升级为硬规则；放弃固定 5～10 行的状态限制。
- **验证状态：** Skill 创建并安装，前置元数据做了直接 UTF-8/frontmatter 检查；当时 `quick_validate.py` 因环境缺少 `PyYAML` 未能运行。
- **证据：** 会话 `019e74f2-adb3-7790-acce-2e982fa88c1f`；摘要 `2026-05-29T18-15-21-6W07-workflow_state_distiller_skill_repeated_feedback_principles.md`。

## 阶段二：形成“证据强度—最窄解释—可撤回”的成熟基线（截至 2026-07-20）

- **目标：** 防止模型把一次反馈推断成用户的长期人格、跨项目偏好或已经确认的原则。
- **原有状态：** 初版已经能从反馈恢复共同目的，但需要更明确地区分一次局部修正、暂时工作假设和长期原则。
- **问题或新证据：** 同一句不满意可能来自不同原因；一个解释即使能复述当前反馈，也未必能预测相邻场景。模型若只追求“理解得更深”，容易扩大解释范围并覆盖用户明确要求。
- **形成的理解：** 理解应按明确事实、局部修正、工作假设、候选原则、已确认原则和硬边界分级。提升依据是用户确认、独立证据、适用范围和预测力，不是出现次数；反例可以使已确认原则缩小、替换或撤回。
- **实际修改：** 建立六级理解状态；要求先保留用户原意与实际事实，再提出一到三个范围最小、可被反例推翻的解释；只有不同解释会改变目标、交付对象、结构、权限或用户可见结果时才提问。
- **保留边界：** 工作假设可以指导当前低风险行动，但不能写成用户已经确认的长期事实；明确硬边界立即生效，不需要反复出现。
- **否决或缩小的路线：** 不推断用户人格和心理原因；不把“反馈出现三次”作为升级原则的机械阈值；不为了展示理解过程而打断任务。
- **验证状态：** 保留了完整只读基准，可与后续渐进状态重构比较。
- **证据：** `prompt-lab/backups/workflow-state-distiller.before-progressive-state.20260803-172153/workflow-state-distiller.SKILL.md`，文件内容时间为 2026-07-20。

## 阶段三：从“纠偏总结器”扩展为渐进形成任务规格（2026-08-03 17:21 前后）

- **目标：** 让 Skill 不只在用户反复否定后工作，也能处理项目开始时目标、背景、输出和边界尚未完整形成的情况。
- **原有状态：** 7 月版本主要围绕纠偏、禁令和隐含目的，虽然已有当前状态，但没有把“不完整规格本身是正常状态”放到中心位置。
- **问题或新证据：** 用户往往需要通过比较、试用和实际成果才能形成偏好。要求其预先回答完整问卷，会把任务设计责任推回用户；另一方面，只靠模型猜测又会扩大未经确认的理解。
- **形成的理解：** 任务状态由目标、上下文、输出形态和边界四类内容组成，可以暂时残缺。应从已经明确的部分开始，选择继续行动、提供可逆样本或提出一个高决策价值问题，让规格在协作中逐步形成。
- **实际修改：** description 扩展到项目开始时无法完整说明需求的场景；正文增加四类任务状态、渐进更新、局部校准与路线切换、失败路线保留条件，以及“询问、试探或继续”的决策价值判断。
- **保留边界：** 渐进形成不表示模型可以用猜测填满缺失字段；高风险、权限和不可逆后果仍需确认。
- **否决或缩小的路线：** 不采用固定问卷；不以“完全理解用户”为停止提问的条件；不重新展开所有历史来寻找抽象规律。
- **验证状态：** 修改前的 7 月基准已保存；修改后的下一阶段快照为 `SKILL.md.bak-20260803-before-positive-distillation`。
- **证据：** 会话 `019fc5a2-e921-7b51-abec-becabca45b58` 的压缩与 Skill 可执行性审查；备份目录 `workflow-state-distiller.before-progressive-state.20260803-172153`。

## 阶段四：压缩规则，但改用普通语言和与证据相称的力度（2026-08-03 21:51 至 23:18）

- **目标：** 降低 Skill 自身的规则负担，让模型更容易执行，同时保留会改变理解范围、下一步和提问行为的作用。
- **原有状态：** 渐进状态版本约 12.8 KB，包含多处同义解释、候选问题形式和重复边界。虽然较完整，但容易把重要决策淹没在说明中。
- **问题或新证据：** 单纯减少字数可能丢失语义；单纯减少否定句又可能删掉真实安全边界。部分术语如“理解强度”“决策价值”虽准确，但普通中文可以更直接地表达同一行动。正向要求也可能被写得过强，例如把“优先简洁”变成“所有回答必须极短”。
- **形成的理解：** 精简应以行为为准，而不是以长度为准。规则措辞要和证据强度相称：局部修正、工作假设、候选原则、默认要求和硬边界使用不同力度；只有会改变下一步的问题才值得问。
- **实际修改：** 将长版重构为“维护的任务状态—理解有多确定—要求写多重—六步蒸馏流程—正向目的—失败与当前状态—验收”；将抽象术语改成普通中文；description 连续缩短两次，最终只保留触发范围，不在 frontmatter 重复正文流程。
- **保留边界：** 仍保留证据来源、范围、反例、撤回机制、硬边界和高价值提问；不能把文件更短当作验收成功。
- **否决或缩小的路线：** 不保留完整候选问题教程；不把所有负面表达一律删除；不让 description 变成整份 Skill 的摘要副本。
- **验证状态：** 现存五份连续快照能够还原每次变化；从第一份到普通语言版为大规模结构重写，后两份只调整 description。
- **证据：** `SKILL.md.bak-20260803-before-positive-distillation`、`SKILL.md.bak-20260803-before-plain-strength`、`SKILL.md.bak-20260803-231523-before-description-slim`、`SKILL.md.bak-20260803-231856-before-semantic-description-slim`、`SKILL.md.bak-20260803-232737-before-deletion-test`。

## 阶段五：加入删除测试和行为前向测试（2026-08-03 23:27 起）

- **目标：** 把“减少规则”从抽象愿望改成能够判断一句话是否仍有独立作用的验收方法。
- **原有状态：** Skill 已要求只保留会改变下一步的内容，但“会改变行动”还没有展开为稳定、可重复执行的检查项。
- **问题或新证据：** 模型可能因为一句话看起来更安全而保留同义禁令，也可能为了追求正向表达或更短文本删掉必要边界。
- **形成的理解：** 删除一句后，如果适用范围、下一步、提问、权限和风险处理都不变，该句已被其他要求覆盖；反向边界只有在删除后会重新放入具体、易复发或高风险错误时才保留。
- **实际修改：** 将第三步改为用下一步行动检验理解；在正向目的、验收和维护规则中加入逐句删除测试；评估方法改为覆盖应该触发、容易混淆和不应触发的案例，并比较范围、力度、行动和是否提问。
- **保留边界：** 删除测试不是字数测试；安全、权限、不可逆影响和正向原则无法可靠覆盖的重复错误仍可保留明确禁令。
- **否决或缩小的路线：** 不以“否定句更少”证明规则更好；不让多个解释在导向同一安全行动时继续占用当前状态。
- **验证状态：** `references/eval-cases.md` 增加相应删除测试验收；8 月 3 日的相关 Skill 审查记录为成功。
- **证据：** 会话 `019fc5a2-e921-7b51-abec-becabca45b58`；修改前备份 `SKILL.md.bak-20260803-232737-before-deletion-test`。

## 阶段六：补上“理解形成后应该保存到哪里”（2026-08-04 至 08-06）

- **目标：** 防止蒸馏得到正确结论后，把项目事实、项目规则、样本、跨项目方法和全局规则混写进同一个文件。
- **原有状态：** Skill 能判断理解是否应该升级为长期原则，却没有完整回答确认后的结论应写入哪一层。
- **问题或新证据：** 《崩坏三》RP 校准中同时产生了写作取舍、下一场剧情事实、测试样本和宿主部署规则。用户还说明：当前 Codex 把概念上的全局规则部署在 model instructions files，是因为真实全局 `AGENTS.md` 会被所有 subagent 读取；部署位置不等于规则职责发生变化。
- **形成的理解：** 保存位置由适用范围和用途决定：当前成果留在当前任务；人物、剧情、产品状态进入项目事实或状态文件；项目反复执行的取舍进入项目规则；跨项目按任务触发的方法进入 Skill；所有任务默认规则属于全局职责层；样本和失败记录只是证据。宿主部署方式与概念职责要分开。
- **实际修改：** 8 月 4 日原始补丁曾在 `SKILL.md` 增加完整的“决定保存位置”章节，更新 description 和 `agents/openai.yaml`，并在 `eval-cases.md` 增加案例十五、十六。这段完整正文后来已从当前 `SKILL.md` 删除；用户于 2026-08-12 回看后判断，这应该是自己有意收敛。当前 description、UI 元数据和评估案例仍保留这项能力。
- **保留边界：** 用户没有要求形成长期资料时，蒸馏结果先用于当前任务；同一事实或规则只保留一个主要来源；通用 Skill 不复制某个项目的具体文件清单。
- **否决或缩小的路线：** 不把所有结论写进项目 `AGENTS.md`；不因样本获得认可就把测试内容当成已经发生；不为了形式一致同时写入全局 `AGENTS.md` 和 model instructions files。
- **验证状态：** 当时运行 `quick_validate.py`，三类前向情境和删除测试通过；案例十五、十六当前仍存在。
- **证据：** 会话 `019fcd1d-f325-7530-9dd7-e7a5ac839a4e`；摘要 `2026-08-04T14-11-59-SdaK-honkai3_rp_agents_actionability_and_workflow_state_routing.md`；原始补丁位于该会话 JSONL 第 1450、1462 行附近。

## 阶段七：收窄隐含目标的权限，且不把一次审查自动升级为 Skill 修改（2026-08-06）

- **目标：** 让 Skill 能帮助理解用户没有逐字写出的协作目标，同时阻止模型用“更深层目标”推翻明确指令或扩大范围。
- **原有状态：** 动态状态和隐含目的机制已经存在，但“真实目标优先于表面指令”这类概括可能被模型解释得过强。
- **问题或新证据：** 用户指出助手会为了完成表面目标走极端路线，增加惊扰、操作和成本；随后又明确纠正，本轮是使用现有 Skill 审查原则，不是立即改写 Skill。
- **形成的理解：** 明确指令确定交付结果；隐含目标主要影响路线、信息密度、主动程度和验证方式。未经确认的目标只能作为候选解释，不能单独授权扩大范围、改变结果或降低必要验证。低扰动、正常、可逆路线是选择偏好，不是覆盖明确要求的上位命令。
- **实际修改：** 本次没有修改 Skill。收窄后的原则保留为会话工作理解，等待更多证据或用户明确确认。
- **保留边界：** “节省额度和精力”不能变成少查证、少验证或少报告；“主动推进”不能变成静默执行高影响动作。
- **否决或缩小的路线：** 放弃“真实目标优先于表面指令”的绝对说法；不因发现一个新问题就立即重写 Skill。
- **验证状态：** 概念审查完成，但没有文件修改，也没有用户确认其为新的永久规则。
- **证据：** 会话 `019fd7a5-9060-7a51-be4c-90d359ad0d44`；摘要 `2026-08-06T15-16-19-OMEk-implicit_goals_distiller_principle_audit.md`。
