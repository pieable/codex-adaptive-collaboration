# 修改记录

这份记录用于保存 `write-instructions-zh` 为什么形成现在的写法。精确文本由备份承担；这里保留旧设计解决的问题、新问题怎样出现、修改目的和取舍，供用户以后重新理解和继续调整。

## 2026-08-12

### 为什么开始区分生效规则、修改理由和精确版本

最初的提示词编写流程主要关注怎样写好当前生效文本。随着 Base Instructions 和多代理规则经历多轮校准，单靠当前文件已经无法回答一条规则为什么存在；把旧规则和调试经过都留在生效提示词里，又会让模型把历史问题误当成当前任务。

因此，Skill 增加了版本记录方法：生效文档只保存当前正确规则，Markdown 记录保存修改理由，Git 或只读备份保存精确差异。这样既能让运行中的模型看到干净的当前指导，也能在以后改坏或产生争议时追溯来源。小型措辞修正不要求机械记账，具体反例仍留在校准材料中。

### 为什么“修改理由日志”还不够

第一版方法虽然要求记录日期、修改范围、触发问题和新判断，但仍然容易被执行成一张操作清单。这样的日志能证明改过什么，却不能帮助用户以后理解：原规则当时为什么那样写、它已经解决了什么、后来为什么还要改，以及新版本保留或牺牲了哪些作用。

这次问题在恢复“自主性与受阻换路”规则时变得明确。只把经验概括成“保留决策顺序、不要设置硬门槛”，仍然过于针对当前文本；真正需要保存的是旧设计的形成背景、原问题、新证据、当前目的和取舍过程。

因此，Skill 把 Markdown 文件重新定义为可供人阅读的提示词演变记录。重要修改应从原有设计和它解决的问题写起，再说明新问题与本次目的，最后交代实际改变、保留与放弃的路线及验证状态。日期、哈希、命令和备份降为证据索引，不再主导正文。修改流程也相应增加“先还原旧设计目的”，避免解决新问题时无意破坏旧规则已经承担的作用。
### 为什么只写自然叙述仍然不能恢复一致愿景

- **目标：** 让后来修改提示词的新模型不只是了解因果，还能迅速还原用户始终一致的理想状态，并比较每一阶段怎样服务这个愿景。
- **原有状态：** 上一版已经要求说明旧设计、新问题、修改目的和取舍，但强调“自然叙述、不要求固定表格”。
- **问题或新证据：** 实际重写多代理演变记录时，这条规则产出了连续的大段文字。内容虽然比流水账完整，用户仍然很难定位目标、问题和修改关系，新模型也不容易从不同阶段抽取同一套判断结构。
- **形成的理解：** 可读性既需要真实因果，也需要稳定的信息位置。结构化字段不是为了机械填表，而是让最终愿景、旧作用、新问题、修改和验证能够被人和模型快速比较。
- **实际修改：** Skill 要求长期复杂记录先写整套提示词的最终愿景；每个阶段使用目标、原有状态、问题或新证据、形成的理解、实际修改、保留边界、否决路线、验证状态和证据。简单变化可以合并或省略空项。
- **保留边界：** 不要求为了填满字段重复内容；精确操作、哈希和命令仍留在证据位置；生效提示词仍不混入历史。
- **否决或缩小的路线：** 放弃纯流水账，也放弃没有稳定结构的一大段发展叙述。
- **验证状态：** 已按新结构完整重写多代理提示词体系演变记录；尚需在下一次不同提示词修改任务中验证通用性。

## 2026-08-13

### 为什么修改前要主动读取演变记录

- **目标：** 让每次提示词修改都延续同一套最终愿景，避免模型只根据当前一句规则做局部修补。
- **原有状态：** Skill 已要求从现有文本、旧版、演变记录和校准材料还原背景，也规定演变记录保存旧设计、新问题和取舍。
- **问题或新证据：** “从多种材料还原”没有明确阅读顺序，模型仍可能只看当前生效文本，或者把演变记录当作修改完成后才补写的日志。当前文本只呈现现行规则，无法单独说明旧设计为什么形成、哪些路线已经否决、哪些作用必须保留。
- **形成的理解：** 演变记录应当同时服务于修改前的理解和修改后的保存。对于已经经历多轮校准的提示词，先读演变记录能够用较少材料恢复最终愿景和关键取舍；记录缺失或不足时，再查旧版、备份、会话证据和校准材料。
- **实际修改：** 修改流程第一步明确要求先定位并阅读对应演变记录，用它补足最终愿景、旧设计目的、已否决路线和保留边界；同时禁止把日志中的历史规则直接复制回生效文档。
- **保留边界：** 当前生效文件仍是规则权威来源；演变记录用于解释和校准，不覆盖用户当前要求，也不替代对当前文本和真实行为的检查。小型且没有设计影响的措辞修改仍不需要机械扩展历史调查。
- **验证状态：** Skill 文本和本记录已更新；本轮浏览器职责修改已经按该方法回看现有 R17 和体系演变记录。尚未在新的独立提示词任务中验证触发稳定性。
### 为什么精简要先删除无效规则并做最终语义检查

- **目标：** 在减少提示词长度的同时保持原有行为，让每个角色只读取能够指导其行动的规则，并在完成修改后主动发现语义漂移。
- **原有状态：** Skill 已要求不重不漏、按语义分段、恢复旧设计目的并验证文本、同步和行为；但没有明确区分“删除无效上下文”和“压缩有效决策边界”，最终检查也没有要求核对阅读者的实际能力。
- **问题或新证据：** 多代理共享规则曾把委派、`fork_turns`、线程复用、浏览器创建和工作区编辑说明同步给所有角色。四个不能创建 subagent 的直接执行者因此读取了约 600 字无效委派规则，浏览器执行者甚至看到要求自己创建 `browser-operator` 的自指说明；只读角色也读取工作区编辑规则。与此同时，自主性、最小方案和线程复用等长规则控制多个真实决策分支，压成一句会重新产生旧误判。
- **形成的理解：** 精简的第一选择应是删除不适用于阅读者、已经被覆盖或不会改变行为的内容；只有确认被删除细节控制的行为仍由其他规则承担时，才合并有效文本。提示词长度本身不是目标，角色能力、语义完整性和行为一致性才是。
- **实际修改：** 编写原则增加上述精简顺序；修改流程要求检查触发条件、优先级、决策顺序、例外和行为边界，并在完成后对照用户目标、最终愿景和保留边界重新通读，同时核对规则与阅读角色的工具和能力。
- **保留边界：** 不要求所有长规则继续保留，也不把每次精简变成机械测试表。能够确认不改变行为的重复、无关或失效内容应直接删除；真实误判形成的必要分支和安全边界继续保留。
- **验证状态：** Skill 已更新，并在同一轮多代理提示词重构中用于识别和移除能力不匹配的共享区块；静态同步和角色区块矩阵仍待最终检查，真实任务行为待新任务验证。

### 为什么目的、背景、结果和边界不是固定模板

- **目标：** 让提示词先把行动写清楚，同时在真正需要时给模型足够的信息作出正确取舍。
- **原有状态：** 用户从 OpenAI 开发者文档中形成了“目的或目标、背景、结果、边界”的理解，并在原有 subagent 提示词开头直接写明角色目标。Skill 要求优先写希望采取的行动，也允许提供目的、原因和两三个例子，但没有说明四类信息各自什么时候值得写、什么时候可以省略。
- **问题或新证据：** 把目的、背景、结果和边界理解成每条指令都必须包含的四项，会让简单规则变长，并把编写方法误用成固定格式；完全只写动作，又可能在规则冲突或情境变化时缺少判断依据，也会漏掉能够支持多种行动的背景知识。
- **形成的理解：** 四类信息承担不同决策功能，也不要求同时出现。目标为规则取舍和未列情境提供方向；背景建立当前状态、成本、能力和机制等事实模型；结果给出可观察的交付物、完成状态或验收证据，不是重复目标；边界划定允许范围、必须保持的内容和停止条件。“怎么做”是指令本身，通常应直接表达；例子用于校准歧义。例如模型成本差异并不直接规定每次委派，却能让 Root 根据任务结构自主选择执行者。
- **实际修改：** 编写原则分别写清目标、行动、背景、结果和边界的使用方式：先用目标统领完整提示词，具体行动直接表达，四类信息按行为价值选用；成本、角色能力和工具机制等背景事实可以代替对每种情境分别列规则；结果写成可观察的完成证据；边界可以直接使用禁止性表述。
- **保留边界：** 不把四类信息变成固定模板，也不把“优先正向行动”升级为禁止写“不能做什么”。简短目的、原因和背景知识仍用于帮助模型在规则冲突或新情境中判断应保留什么；例子只校准一般规则。
- **验证状态：** 已用于重写多代理委派规则：用一句目的解释上下文隔离，再直接规定何时委派，并用大范围资料读取、长日志处理和连续页面操作三个例子校准“一次调用也可能产生大量输入”。真实新任务行为仍待验证。
