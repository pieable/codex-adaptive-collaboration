# 提示词与规则编写

目标：把生效文档写成自然、清楚、可以直接执行的当前指导，同时给模型足够的判断依据处理未列情境。重要提示词和长期规则由主 agent 理解和编写；格式处理、固定映射和多处同步可以交给 `worker`。

## 执行步骤

1. 确认权威文件、修改范围、目标行为、必须保持的内容和实际阅读角色。
2. 修改成熟规则时，先在演变记录中搜索这条规则或所在章节，只读相关阶段；信息不足再查旧版、备份、会话证据和校准材料。
3. 检查现有规则是否已经产生同一效果，并确定这次修改应放在哪个章节、由哪条规则负责。
4. 选择能够保留原有作用并解决新问题的写法，在最小范围内修改。
5. 写完后，把自己当作第一次看到该文件的运行模型，通读改动所在的完整章节。每条规则都应直接写清适用条件、行动和停止点；同一行为只规定一次，条件、行动、例外、原因和连续步骤写在一起；使用具体对象和动作，不依赖抽象词，也不要求跨段拼接含义。确认相邻规则没有冲突或遗漏，发现问题先改，再进入验证。
6. 按完成条件验证文本、同步、加载和真实行为；交付时说明修改内容、保留边界、验证层次和未验证部分。

## 规则写法

- 先判断正在修改的是操作规则，还是人格、语气和用户协作。操作规则先写目标或必要背景：固定工作写步骤，常见分叉写清条件和行动，需要模型判断的工作写清目标、判断标准和边界，把边界内未指定的选择留给模型，低频或高风险路径给出明确做法。人格、语气和用户协作保留稳定体验目标、情境适配和少量校准例子，不按普通流程机械压缩。
- 目的、背景、结果和边界只在能够改变理解、取舍或执行时加入。结果写成可观察的完成状态。
- 一般规则表达适用范围；两三个例子只用于校准容易误解的边界。
- 生效文档只呈现当前指导；修改理由和版本历史分别进入演变记录与版本控制。

## 功能块基线与测试

- 新提示词先列出它必须承担的全部职责，再为每项职责写一组能够独立生效的最小规则。成熟长提示词先保存完整版，再建立覆盖相同职责的精简基线。
- 真实任务反复出现同一种错误时，只扩展对应规则块，并同时测试一个容易混淆但不应触发的场景；模型、宿主或关键工具变化时，从同一基线重新测试。
- 平台机制、权限和安全边界按当前环境核对，并保留对应功能块。

## 演变记录

- 记录开头写整套提示词的最终愿景。重要阶段按需写目标、原有状态、问题或证据、形成的理解、实际修改、保留边界、否决路线和验证状态。
- 小型措辞修正可以省略记录；改变设计目的、适用范围、触发条件、权限、停止条件或重要写作判断时更新记录。
- 日期、会话、哈希和命令作为证据索引，正文以发展过程和判断为主。
