# 提示词编写

## 目标

让提示词在真实使用中持续产生用户期望的行为，并在模型、宿主和工具变化后，仍能以较低的维护成本保持这种效果的一致性。写出的指导既保留长期校准形成的有效经验，也能迁移到未列出的情境。

## 确定提示词需要说明什么

从以下五个方面还原用户希望模型怎样工作。根据实际需要选择其中的内容，形成提示词的骨架。

- **目的：** 希望通过这块提示词让模型做到什么。
- **背景：** 模型理解任务和作出判断需要知道什么。
- **行动：** 模型需要做什么。
- **结果：** 模型做完后要交付什么，怎样判断已经完成。
- **边界：** 需要保持什么，模型可以行动到什么范围，以及何时停止。

长期维护时，骨架承载需要跨版本保持的内容。当前模型、宿主和工具所需的说明、例子和固定协议构成“血肉”。环境变化时，先核对骨架，再复审血肉。

## 结构

提示词按稳定主题组织。标题直接说明本节的对象、情境或责任，使第一次阅读者只看目录就能定位内容。

结构应当表达规则之间的统摄关系。先找出一组规则共同服务的责任或判断，把共同原则写在上位，再把需要分别处理的差异放在它下面。不要只把原有句子拆成更多标题、段落或列表。

一个标题优先表达一个完整概念。内容能够独立展开且足以成节时再拆分，较短内容留在更大的自然主题中。

同一个判断能够用一句自然的话说清时，直接写成一句。内容包含多个独立规则或真实的从属、并列、步骤关系时，再用相应结构展开。

标题层级表达内容的真实从属关系。根据内容需要使用相应层级：

```markdown
# A

## B

### C

# D

## E
```

没有先后关系的并列内容使用无序列表，从属内容放在对应的上位内容之下：

```markdown
- 并列内容
- 并列内容
  - 从属内容
```

真实的步骤、阶段、优先级或判断顺序使用有序列表：

```markdown
1. 第一步
2. 第二步
3. 第三步
```

多个独立规则分别写清，不用分号压成长句。章节可以长短不一，使用能够准确表达语义关系的最浅层级。根据实际内容选择需要的形式和层级。

## 编写流程

### 明确本次要改变的表现

先说清楚这次想让模型在哪种情况下改变什么表现。把现在已经做对、需要继续保留的部分也记下来，避免修一个问题时破坏其他效果。

用户会记得多次任务中发生过什么，当前模型通常只看到这一次。因此，用户反复指出的体验和实际代价是判断问题的重要线索。涉及文件状态、运行记录或失败原因时，再查看当前文件和记录核实。

先确认这次的问题能不能靠修改提示词解决。提示词里已经有相关规则，模型却仍然没有形成预期行为时，再判断是规则本身没有说清楚，还是问题根本不在提示词。问题不在提示词时，修改真正出问题的地方。

### 恢复现有提示词的来路

这一阶段是为了知道现有规则为什么存在，避免精简时删掉过去解决过的问题。

修改已经使用一段时间的提示词，先看当前文本、修改日志和保真并集。能从这些材料看清相关规则的目的和已经否决的路线，就可以开始写。只有看不清时，才继续查 Git 历史、旧版、备份或以前的会话。

新建提示词没有这些历史，直接从真实用途和代表性例子开始，先写够当前使用的版本，不为假想的未来增加结构。

从当前对话和旧任务中提取未来仍然需要生效的规则和背景，把它们写进目标模型会稳定读取的位置。会话原文和只用于这次判断的例子留在修改材料中。

### 确定规则放在哪里

一条规则应该写在哪里，先看谁需要读到它，以及谁负责按它工作。

- 共同工作方法写入共同读取的提示词。
- 角色自身的问题写入该角色的指令。
- 项目事实和工作方式留在项目层，会变化的配置事实靠近当前配置来源。

一个问题同时来自多个位置时，各处分别修改自己负责的部分，不把整套规则复制到每个文件。

### 写成当前指导

编写时，把阅读提示词的模型当作一个有不错理解能力的人：

- 使用清楚、直接、普通人一遍能读懂的语言。先说明这块是做什么的，再直接写谁做什么。需要解释原因时，用具体情况和例子把因果和动作写完整。
- 只写模型在实际使用时无法从其他地方可靠知道，或者值得长期提醒的内容。例如用户确认的长期偏好、目标模型不会从其他地方看到的项目规则，以及一旦忽略就会造成高代价的权限边界。
- 修改成熟提示词时，先改相关规则并保留没有问题的原文。当前标题和段落已经不能准确表示内容之间的关系时，重新组织结构。重组后确认原来的有效规则都有去向。两句话看起来相近时，也要确认它们实际管的是同一件事再合并。
- 现实中的情况通常列不完，也不靠列举来指导模型。先找出这些情况共同影响的判断，写清它在什么情况下怎样改变行动。提炼后的原则要让第一次阅读的模型可以直接使用。模型仍需猜测概括词指什么时，恢复必要的具体说明。每一项本身需要分别处理时，才保留列表。
- 优先写希望模型怎样做。正向指导仍然管不到明确边界，或者同一个问题在正向规则下反复出现时，再增加只针对这个问题的禁令。
- 普通、容易纠正的选择给模型发挥空间。错误代价越高，规则写得越明确。措辞力度跟证据和风险相称。没有写明的普通选择由模型在已有目的和边界内决定，也不会扩大权限。
- 难以只靠规则说清楚的语气、关系或感觉，可以附上少量真实例子。例子帮助模型理解规则怎样使用，适用范围仍由明确规则和边界决定。

### 通用审查

通用审查检查提示词本身有没有写对、写全和写在正确的位置：

- 对照本次想改变的表现、相关历史和会与这次修改一起生效的规则，检查新版本是否只改变了用户确认的部分。
- 保真并集中的有效规则都要有去向。继续使用的留在正文，应该换位置的移到正确文件，已经失效或被取代的删除并在修改日志中说明原因。
- 新版本应当让第一次看到它的目标模型在真实任务中也能照着做，并从提示词本身获得所需说明。文字是否容易理解由人工复审，行为是否正确留到实际使用验证。另一个模型只读后表示能够理解，只能作为文字层面的参考。
- 检查是否使用了生造词或含义不稳定的概括词。目标领域已有、含义明确而且目标模型能够稳定理解的术语可以直接使用。其他词改用普通语言，必要时在首次出现时说明含义。
- 文件变短、目录更整齐或新文字读起来更连贯，都不能证明原来的效果还在。只有所有需要这条规则的模型都会稳定读到新位置时，才从旧位置删除。

### GPT-5.6 模型专项审查

通用审查完成后，再逐句检查 GPT-5.6 写提示词时反复出现的问题：

- **防御性否定：** 逐句查看“不要”“不是”“不等于”等否定写法。正面说明已经足够时，直接写希望模型怎样做。仍然容易混淆的边界和高代价错误，保留明确而且范围窄的禁令。
- **过度枚举：** 看模型是否仍要逐项扫描一组词才能作出判断。几项内容共同影响同一个判断时，直接写清这个判断怎样改变行动。每项都会独立改变行动时，才逐项保留。减少项目数量或改写成一整句没有解决问题。
- **过度抽象：** 提炼后的文字应当让第一次阅读的模型直接照着做。模型还要猜概括词指什么或怎样行动时，恢复必要的具体说明。能够帮助理解原则的少量差异和例子继续保留。
- **分号长句：** 检查全文是否使用分号连接规则。同一个判断写成一句自然的话。内容承担不同责任时，按真实的统摄、从属、并列或步骤关系重新组织，不用分号代替结构。

其他模型维护本 Skill 时，把这一节改成针对该模型反复出现的问题。

### 验证实际效果

有可用环境时，让目标模型或实际宿主使用修改后的提示词。任务风险越高，验证越接近真实使用。

暂时不能实际试用时，只完成文字审查，并明确告诉用户验证停在这里。文件已经写入、宿主已经加载和模型真的按预期工作，是三个不同的结果。

### 保存修改记录

生效提示词只写当前应该遵守的指导。仍然帮助模型理解和取舍的原因留在正文，只用于解释某次修改的历史原因写进修改日志。

规则储藏库保存历代规则、来源和当前状态。保真并集保存所有仍然有效的规则语义。

重要提示词优先使用已有 Git 仓库。项目已经有仓库时沿用这个仓库，不在里面再建一个仓库。没有仓库并且范围清楚时，可以建立只保存在本地的仓库。

修改前确认原来的状态能够恢复，保留与本次无关的改动。修改后查看真实差异，并用提交说明这次改变了什么行为。Git 保护不到本次修改时，再使用只读备份。

维护或重写本 Skill 时，先建议用户全程看着修改，并逐步确认关键变化。每次只改实现已确认变化所需的内容，同时读取 `references/eval-cases.md`。普通提示词任务不读取这个文件。
