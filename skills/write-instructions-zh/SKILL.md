# 提示词与规则编写

把生效文档写成自然、清楚的当前指导手册。重要提示词和长期规则由主 agent 直接理解和编写；格式处理、固定映射和多处同步可以交给 `worker`。

## 开始前

先确认权威文件、本次要改变的行为、允许修改的范围，以及必须保持不变的内容。用户没有要求调整、也没有证据表明存在问题的成熟内容，默认视为有意保留。

区分规则来源和适用范围：主 agent 调度、所有 agent 共有、角色专属、环境执行、项目内部和当前配置事实分别放在对应位置。需要让多个角色看到一条规则，不等于把不同方向的规则合并成同一章节。

## 编写原则

- 遵循不重不漏：每条规则有明确作用，已有规则能够产生相同行为时不再重复增加。
- 优先写希望采取的行动。禁令用于正向原则覆盖不到的硬边界、高风险行为或反复出现的问题，并写清被禁止的具体行为。
- 把阅读者当作理解能力良好的模型。提供足以判断的信息、目的和原因，给正常情境保留发挥空间；不把每个动作拆成机械步骤。
- 生效文档只保留当前正确的规则。用户否定或替换旧规则后，直接删除旧表述并写入当前规则，不留下调试过程、修改历史或“不要旧做法，而要新做法”的痕迹。
- 段落、标题和列表表达语义归属。条件与行动、原则与例外、原因与结论、连续流程和同一列表项保持在同一规则单元；只有能够独立成立的方向才另起段落或章节。
- 规则力度与证据、适用范围和风险相称。局部要求写清“这次”，暂时理解写清“目前先按”，一般偏好使用“默认”或“优先”；只有明确硬边界和高风险要求使用“必须”“不得”“绝不”。
- 使用清楚、直接、普通人一遍能读懂的语言。可以用两三个例子校准容易误解的边界，但例子不能代替一般规则。
- 精简时先删除不适用于阅读者、已由其他规则覆盖或不会改变行为的内容；不要为了缩短字数，把控制不同决策分支的条件和边界合成一句。

## 版本记录与生效文档

持续复用、经过多轮校准或会影响大量后续任务的提示词，应当分别保存当前规则、发展与修改过程，以及精确版本。

- 生效的提示词、`AGENTS.md`、Base Instructions 或 Skill 只保留当前正确的规则，不混入旧版本、调试过程和已经否定的方案。
- 在同一项目或规则目录维护供用户和后来维护者阅读的 Markdown 演变记录。它的作用是让人重新理解这套提示词为什么会发展成现在这样，不是罗列日期、文件和操作的流水账。
- 记录开头先写整套提示词始终一致的最终愿景，使新模型知道用户最终想达到什么状态。复杂或多阶段演变使用稳定字段，让不同阶段可以快速比较：
  - **目标：** 这一阶段想达到什么，以及怎样服务最终愿景；
  - **原有状态：** 修改前怎样工作，为什么曾经这样设计；
  - **问题或新证据：** 原设计出现了什么新缺口，或者原判断被什么修正；
  - **形成的理解：** 对原因、适用范围和取舍产生了什么新认识；
  - **实际修改：** 当前规则、结构或执行方式具体怎样变化；
  - **保留边界：** 旧设计已经解决的哪些问题不能在修改中丢失；
  - **否决或缩小的路线：** 哪些方案被放弃，以及为什么；
  - **验证状态：** 已验证到文件、同步、加载还是实际行为，哪些仍未验证；
  - **证据：** 需要回查时使用的会话、备份、示例或测试。
  简单变化可以合并字段或省略空项，但不能把结构取消成一大段难以定位的文字，也不要为了填满字段重复同一内容。
- 日期、会话、备份、哈希、命令和精确文本差异用于定位证据与回退，可以集中放在记录末尾或独立索引中，不应盖过发展过程和判断本身。
- 具体场景、反例和逐句纠正保存在校准便签或示例文件中；演变记录说明这些材料怎样改变了理解，提炼后的当前指导才进入生效文档。
- 使用 Git 等版本控制保存精确差异和承担回退。没有版本控制时，使用带日期的只读快照作为替代，且快照不参与当前提示词加载。
- 小型措辞修正不必机械增加记录。修改改变原有设计目的、适用范围、触发条件、行为边界、权限、停止条件或重要写作判断时，应当记录。

## 修改流程

1. 修改已有规则前，先定位并阅读对应的演变记录，用它补足当前生效文本没有呈现的最终愿景、旧设计目的、已否决路线和保留边界；记录缺失或信息不足时，再从旧版、备份、会话证据和校准材料还原。证据仍不足时标明未知，不根据一句旧措辞臆测设计目的，也不把日志中的历史规则直接复制回生效文档。
2. 说明现在出现了什么新问题或新证据、本次目的是什么，以及要改变哪个行动、提问、权限、停止条件、风险处理或验收结果。
3. 检查现有内容是否已经覆盖同一效果。删除一句话不会改变上述行为时，通常不必保留它。
4. 选择能够同时保留旧作用并解决新问题的行为框架，再补充必要边界；不要沿着每次纠正不断累积孤立补丁，也不要为了新问题无意改掉旧规则解决的问题。
5. 在最小范围内修改，把完整规则块移入正确章节，不顺带重排用户或官方保留的内容。
6. 检查正文、标题、段落和列表层级，确认没有拆开条件、例外、因果或连续决策过程；确认改写没有无意改变原规则的触发条件、优先级、决策顺序、例外或行为边界。
7. 修改完成后，对照用户当前目标、演变记录中的最终愿景和保留边界重新通读生效文本。准备删除或合并的细节，只有在它控制的行为已由其他规则覆盖时才移除；同时检查规则是否与实际读取它的角色能力和工具一致。
8. 验证文本完整性、结构归属和行为效果。完成条件涉及加载或同步时，再检查新任务、真实角色或同步脚本确实使用了修改后的内容。

## 交付

说明实际修改了哪些规则、保留了哪些边界、验证到了哪一层，以及仍未经过真实运行验证的部分。不要把编写过程写进生效提示词本身。
