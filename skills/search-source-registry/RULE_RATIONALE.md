# `search-source-registry` 规则理由

本文件不参与运行。它保护 [`SKILL.md`](SKILL.md)、`references/`、`scripts/` 和 `agents/openai.yaml` 的当前职责。用户于 2026-08-30 明确说明：这个 Skill 是所有网络搜索 Agent 可用的通用搜索辅助，为它们提供更权威的入口，使搜索更快、覆盖更好；它不是公司研究 Skill 的附属品。

## SSR-01 只在搜索路线、信源或覆盖会改变结果时触发

- **状态：** `current-effective`
- **行为：** 用于制定搜索路线、按主张判断信源、枚举候选或核验一手材料；已经给定唯一权威来源且只需读取的简单任务不需要额外展开注册表流程。
- **理由：** Skill 的价值是减少盲目搜索和漏项，不是让所有联网查询都加载来源目录。
- **来源：** 当前 description；2026-08-30 用户定位；四份 2026-08-03 备份显示 description 曾因枚举场景过多而逐步收敛。
- **验证：** 当前触发文字清楚；自动触发准确率未做真实任务对照。
- **改变条件：** 新 description 必须继续区分“需要路线或覆盖判断”和“已知来源的一次读取”。

## SSR-02 注册表是搜索入口，不是固定查询或结论系统

- **状态：** `current-effective`
- **行为：** 研究者理解问题、选择来源和查询、判断充分性并形成结论；注册表只帮助决定从哪里开始，程序只做明确的收集、过滤、去重和覆盖记录。
- **理由：** 固定搜索词会随问题变化失效，程序也无法仅凭返回数量判断相关性、完整性或采用结论。
- **案例：** C-13；两路搜索工具返回 2 条而直接搜索有 8 条，说明“程序运行成功”不能升级为覆盖完成。
- **来源：** `SKILL.md` 开头和结尾；`prompt-lab/subagent-architecture/rule-rationale.md` 的来源召回实验。
- **验证：** 历史案例支持职责分离；每个新脚本仍需检查是否越权评分或下结论。
- **改变条件：** 程序可以增加机械信号和过滤，但不能在没有可解释研究标准时输出统一总分或替研究者决定采用对象。

## SSR-03 信源等级针对当前主张判断

- **状态：** `current-effective`
- **行为：** 先把问题改成可核验主张，再找最接近其原始记录的来源。同一个网站对不同主张可能处于不同等级；当事方材料能证明其声明，不能自动证明解释客观或效果最佳。
- **理由：** 给网站永久贴“权威”标签会把官网宣传、用户经验、搜索摘要和独立核验材料错误互换。
- **来源：** `SKILL.md` 第 17 行；`references/general-web-research.md` 的信源等级和主张—原始记录表；2026-08-03 `before-general-source-levels` 备份后的新增规则。
- **验证：** 文字与历史变化一致；不同领域的来源判断仍需按主张核对。
- **改变条件：** 可以新增领域来源表，不能把主张相对性改成网站固定等级。

## SSR-04 覆盖状态必须保留失败、未检查和手工入口

- **状态：** `current-effective`
- **行为：** 记录每个入口是 `ok`、`partial`、`error` 还是 `manual_required`，以及登录、浏览器、适配器和未检查缺口。“没有找到”只说明实际检查范围，不能代替“没有发生”。
- **理由：** 入口失败和返回为空都会造成假阴性。保留缺口才能让上级决定是否换入口、手工补查或收窄结论。
- **案例：** C-13 中 TDK 403、Cohu 超时与找回的遗漏候选同时保留。
- **来源：** `SKILL.md` 第 18、27、33、39–42 行；两个脚本的 `coverage` 输出；`references/general-web-research.md` 的枚举和交回规则。
- **验证：** 脚本结构会保存状态；登记入口的实时可访问性尚未在本轮全部重验。
- **改变条件：** 新来源适配器必须映射到同样可区分的覆盖状态，不能把异常吞成空候选。

## SSR-05 候选只由一个执行者负责，重复必须有原因

- **状态：** `current-effective`
- **行为：** 多人核验时每个候选只有一个负责人。只有来源入口不同、结果异常为空或需要独立复核时才受控重复。
- **理由：** 无条件让多个 Agent 查同一个候选会重复支付搜索、阅读和上下文成本，却不会自动增加覆盖。
- **案例：** C-11 的重复委派和 Root 重查；搜索 v2 的自由派生慢于单 Agent 基线。
- **来源：** `SKILL.md` 第 19 行；全局责任链和并行规则。
- **验证：** 规则存在；真实研究任务中的候选分配仍需观察。
- **改变条件：** 高风险结论确实需要独立复核时可以重复，但合同要写清复核差异和停止条件。

## SSR-06 只读取当前任务相关的 reference

- **状态：** `current-effective`
- **行为：** 通用研究读取 `general-web-research.md`，代码与依赖研究读取 `code-research.md`，指定时间窗内的半导体新闻才使用 `sources.json` 和候选收集程序。
- **理由：** 来源目录是按需披露的领域材料。全部加载既浪费上下文，也会让半导体入口或代码采用规则污染无关研究。
- **来源：** `SKILL.md`“怎么用”；Skill Creator 的渐进式披露原则。
- **验证：** 路由静态清楚；真实 Skill 使用时是否只读相关 reference 未验证。
- **改变条件：** 新领域形成稳定、可复用并会改变搜索决策的来源集时可以增加独立 reference，并从 `SKILL.md` 写明触发条件。

## SSR-07 通用搜索按原始记录、引用链和停止条件推进

- **状态：** `current-effective`
- **行为：** `general-web-research.md` 先定位产生原始记录的机构或系统，再用低等级来源发现正式名称和原始链接；逐条记录材料实际证明的内容。冲突先比较对象、定义、时间、版本和地区；下一份来源不能改变结论、覆盖或未知时停止。
- **理由：** 直接搜索问题原句容易停在摘要和转载；固定链接数量又不能代表充分性。
- **来源：** `references/general-web-research.md`。
- **验证：** 规则与 Deep Research 的证据结构一致；各类来源入口仍需实时核验。
- **改变条件：** 高风险或自利来源需要独立材料，单一明确事实已由当前一级材料覆盖且无冲突时不机械增加链接。

## SSR-08 代码研究先确认本地需求，再找成熟候选

- **状态：** `current-effective`
- **行为：** `code-research.md` 先确认本地技术栈、版本、依赖和不能改变的接口，再依次检查项目已有能力、标准或平台能力和成熟生态候选。采用时检查功能、维护、集成成本、风险、许可证和可验证性；不适合整体引入时可学习机制或移植最小部分。
- **理由：** 搜索代码的首要价值是少写不必要的新代码，但只看 Star、下载量或第一个能运行的项目会引入不适配依赖和长期维护成本。
- **来源：** `references/code-research.md`；Root Base 和 `code-development` 的最低复杂度/Ponytail 历史。
- **验证：** 方法有历史依据；候选程序的实时 API 和排序质量仍需基准测试。
- **改变条件：** 当前项目已有可靠实现时直接复用；成熟候选不适配或引入成本过高时才写满足当前目标的最小新实现。

## SSR-09 候选程序只输出机械信号和实际覆盖

- **状态：** `current-effective + conditional`
- **行为：** `discover_code_candidates.py` 枚举 GitHub、Python、npm、Rust、Go 和 NuGet 候选并保留来源查询、许可证、维护、发行和使用信号；`collect_candidates.py` 按左闭右开时间窗收集半导体候选。完成来源查询不表示候选充分，候选也尚未完成事实核验。
- **理由：** 机械枚举适合并行 HTTP、去重和结构化记录，但相关性、成熟度、新闻意义和完整性仍需研究者判断。
- **案例：** C-13 的 EDGAR 来源枚举在约 5.8 秒内产生 8 个候选并找回遗漏项，同时保留失败入口。
- **来源：** `SKILL.md`“已有程序”；两个脚本及 `references/sources.json`；`subagent-architecture/rule-rationale.md`。
- **验证：** 本轮会做语法、帮助入口和无网络参数验证；实时网络覆盖和结果质量另行标记。
- **改变条件：** API、版本或来源结构改变时更新对应适配器；不能以脚本退出码 0 证明研究结论完成。

## SSR-10 Token、任务状态和输出不进入 Skill 目录

- **状态：** `current-effective`
- **行为：** GitHub token 只从 `GITHUB_TOKEN` 环境变量读取；任务状态、游标和输出写到调用者指定的 Skill 外路径；运行现有程序前不要求先把源码读进模型上下文。
- **理由：** 凭据和任务产物不应进入可发布的 Skill，重复加载长脚本也会浪费模型上下文。脚本应通过稳定 CLI 使用，只有修改或排障时才读源码。
- **来源：** `SKILL.md` 第 27、35 行；`discover_code_candidates.py` 的环境变量读取和 `--output`；`collect_candidates.py` 的输出参数。
- **验证：** 当前源码没有硬编码真实 token；输出路径由调用者控制。
- **改变条件：** 可换成宿主安全凭据机制，但不能把密钥、游标或任务输出提交进 Skill。

## SSR-11 上级只对已定位且会改变结论的原文作最小核验

- **状态：** `current-effective`
- **行为：** 实际搜索由 Web Researcher 读取相关来源表并交回候选、覆盖、核验、链接和缺口。Root 或 Research Lead 只在一个已定位的原文差异会改变自己负责的判断时打开所需最小材料，不重新接管整条搜索路线。
- **理由：** 上级负责综合或全局判断，不代表必须亲自发现和重复阅读所有来源；重复搜索会污染高价上下文并增加调用成本。
- **案例：** C-11、C-13；研究搜索和上层判断曾混在一起，2026-08-29 已分离。
- **来源：** `SKILL.md`“委派和直接搜索”；`deep-research`；Agent `PROMPT_HISTORY.md`。
- **验证：** 静态职责一致；真实研究任务的 Root 调用下降仍待验证。
- **改变条件：** 没有多 Agent 时当前责任人可直接搜索；有责任分层时不能把“关键来源”解释成上级必须重做来源发现。

## SSR-12 新入口先证明适用范围和稳定性

- **状态：** `current-effective`
- **行为：** 没有专门来源表时按通用方法搜索。发现新入口后，先核验它能支持哪些主张、覆盖什么范围以及是否稳定，再考虑登记；登记不承诺永久可访问或全球完整。
- **理由：** 临时搜索命中不等于一个入口值得长期维护。注册表若无限加入未经验证链接，会变成更难使用且更易过期的收藏夹。
- **来源：** `SKILL.md` 最后两行；2026-08-03 general source levels 调整。
- **验证：** 当前 `sources.json` 的实时可用性尚需定期检查，不能仅凭登记状态视为有效。
- **改变条件：** 入口长期失效、改变权限要求或不再支持原主张时降级为手工/失败或删除，并在历史中保留原因。
