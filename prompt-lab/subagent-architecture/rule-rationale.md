# Subagent 编排规则理由

本文件说明 `current-rules.md` 中各条规则解决的问题、依据和可观察的失败信号。它不直接加载为运行提示词。

设计主题保留了研究时的编号；当前十条规则与证据主题对应如下：

| 当前规则 | 主要依据 |
|---|---|
| 1 结果优先 | R1 |
| 2 委派与连续责任 | R2、R3、R4、R10、R18、R22 |
| 3 主任务、合同与唯一所有者 | R7、R8 |
| 4 委派后的所有权与等待 | R13、R15、R18、R22 |
| 5 最小必要上下文 | R7、R15 |
| 6 角色职责、受控第二层与启动失败 | R10、R15、R17、R18 |
| 7 一次交回与定向验收 | R7、R12、R13、R18 |
| 8 浏览器、Computer Use 与授权 | R21 |
| 9 候选发现和模型程序边界 | R14、R16、“生成式 AI 以前的成熟做法” |
| 10 动态调整与停止 | R9、R11、R12 |

## R1 结果优先

- 问题：把省钱、速度或上下文纯净设为绝对限制，会在困难任务最需要强模型时阻止升级。
- 理由：架构服务于任务，不应为了证明多 Agent 更便宜而牺牲完成度和正确性。
- 失败信号：为了控制成本保留明显不足的证据；Luna 无法解决关键冲突却不升级；形式上完成但结果不可用。

## R2 四项判断

- 问题：按“搜索、代码、RP”等领域标签路由过于粗糙，同一领域内部的任务结构可能完全不同。
- 理由：独立可分解性和耦合度决定拓扑，规模决定是否值得委派，结果敏感度决定模型和验证强度。四项已足以解释当前主要场景，又不会把 Base Instructions 变成复杂分类表。
- 依据：Google 最新论文版本覆盖 260 种 Agent 配置和 6 个基准；可分解任务适合集中式并行，强顺序任务使用多 Agent 反而下降，工具密度会增加协调成本。博客仍保留较早的 180 配置结果。
- 来源：https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/
- 论文：https://arxiv.org/html/2512.08296v3
- 失败信号：相同领域的任务被固定使用同一种架构；运行时需要填写大量无助于决策的维度。

## R3 委派看模型往返和输入规模

- 问题：按小、中、大或只按工具调用次数决定委派，都会误判。一次工具调用也可能把大量源码、日志、网页或结构化数据送进 Sol；相反，一次只返回几行结果的批量检查没有必要增加交接。
- 理由：无需工具，或一次工具批次只返回少量内容即可完成时，直接执行通常少一次交接。连续多轮探索，或者单步就要读取和处理大量材料时，低成本执行者可以把这些输入和中间判断留在自己的上下文。路由同时考虑模型恢复次数、进入当前上下文的材料量、责任耦合和结果风险。
- 实验依据：2026-08-04 对同一角色配置检查进行对照。Sol 把独立检查合并为一次命令，工具运行 0.164 秒；按相邻两次实际 Sol 请求计算，批量直查路径约带入 311,487 input token。Luna explorer 得到相同结论，但首次交回前用了 13 次模型请求和 425,692 input token，约 87 秒；根任务为创建、等待和接收结果约发生 3 次 Sol 请求并带入 473,837 input token。Explorer 通过 `send_message` 交回后仍继续检查，直到被中断已累计 30 次请求和 1,426,004 input token。Luna 用量来自 rollout `token_count`，CC Switch 当时没有记录这个新子任务的独立请求行。
- 失败信号：只返回少量结果的批量检查被拆给 subagent 后更慢且增加 Sol 恢复；一次大规模读取因为“只有一步”仍由 Sol 承担；当前负责人把独立读取拆成许多模型—工具往返；需要连续探索的过程仍由 Sol 逐步驱动。

## R4 拓扑跟随任务结构

- 问题：统一的层级或并行结构无法同时适合网络搜索、代码开发和连续 RP。
- 理由：低耦合独立分支可以并行；高耦合任务需要保留连续理解；代码等混合任务适合中央主干加隔离分支。
- 依据：Google 的顺序惩罚结果；Anthropic Research 使用 orchestrator-worker 处理 breadth-first 搜索，同时明确指出编码任务通常缺少同等程度的可并行性。
- 来源：https://www.anthropic.com/engineering/multi-agent-research-system
- 失败信号：顺序推理被多次摘要交接；多个 worker 同时修改共享接口；可以并行的搜索仍被串行执行。

## R5 Sol 掌握关键判断

- 问题：主任务只接收 subagent 摘要时，关键事实、隐含判断和不确定性可能留在子上下文中。
- 理由：不能消除压缩损失，只能让主任务直接接触会改变结论的关键证据，同时过滤重复和低价值材料。
- 失败信号：最终结论依赖 subagent 无证据的判断；Sol 重新读取全部材料；或者为了保持上下文干净而拒绝读取关键原文。

## R6 按需探针

- 问题：任务类别不清时直接选择架构容易过度或不足；但每次固定运行探针会增加启动和等待。
- 理由：把探针限制为有信息价值的有限探索；明显任务直接路由。探针已经得到完整答案时一并返回，减少一次交接。
- 失败信号：每个请求都先运行 probe；probe 开始实现或修改；主任务无视画像重新调查。

## R7 完整责任与证据交接

- 问题：任意拆分会把一条推理链压缩多次；主任务重复验收会抵消时间和成本收益。
- 理由：委派可独立验收的责任，并以证据账本传递结论、证据关系、验证、置信度和缺口。普通摘要容易保留显眼结论，却丢失依赖关系、反例和为何排除候选的判断；只有具体矛盾和缺口值得补查。
- 上下文选择：决定权属于创建者。创建者先确定当前责任、权威文件或对象、完成标准和最终边界，再列出测试和结构化来源并与最近对话比较。合同和来源已经承载结果相关信息时使用 `fork_turns: "none"`；用户纠正、已否决路线、输出要求或关键判断仍只存在于最近少量对话，而且再次概括容易失真时，创建者传覆盖这些内容所需的最少有限轮数。继承的对话可以替代合同中重复的背景，不能替代权威目标和验收边界。执行者接收对话后可以利用其中的原始关系，但不负责猜测自己没有收到什么。`fork_turns: "all"` 会继承上级模型、推理强度和完整历史，不能保留命名角色的低成本模型分工，因此不用于日常委派和专用工作流。
- 依据：Magentic-One 的公开提示词显式维护 GIVEN、LOOKUP、DERIVE、EDUCATED GUESSES 和 Progress Ledger；Anthropic 的研究系统要求子代理任务包含目标、输出格式、工具、来源和边界。
- 来源：https://github.com/microsoft/autogen/blob/b0c800255a601ea41f55f2d02373b0058d4cb2c7/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py
- 来源：https://www.anthropic.com/engineering/multi-agent-research-system
- 失败信号：多个执行者进入同一范围；主任务完整重做 subagent 工作；报告缺少来源、行号或未解决项。

## R8 唯一所有者与共享写入

- 问题：并行修改相同文件、接口或状态会产生冲突和不可预测的集成结果。
- 理由：成熟软件协作使用明确所有权、隔离工作区和中央集成；Codex 也通过 worktree 隔离并行 Agent。只按观察角度拆分，会让多个执行者反复读取同一核心材料，既不能减少主任务上下文，也增加摘要损失。
- 来源：https://openai.com/index/introducing-the-codex-app/
- 失败信号：worker 相互覆盖；合并时才发现接口不一致；无人负责最终集成。

## R9 动态调整

- 问题：任务实际范围只能在探索中逐步显现，初始分类不可能始终正确。
- 理由：路由是可修正的工作假设。发现任务更简单时降级，发现冲突、共享状态或高风险时升级。
- 失败信号：为了维持原计划继续无价值搜索；局部任务扩大后仍按单文件修改处理；已经得到答案仍继续派生 Agent。

## R10 能力与验证责任一致

- 问题：只读代理可以很好地定位代码和静态缺陷，但无法运行测试、安装临时依赖或执行真实调用；若让它独自拥有诊断，报告可能停在静态推断。
- 理由：连续性指同一个有足够判断能力的角色持续掌握问题、假设和集成状态，不表示这个角色必须亲自完成全部执行。复杂代码中由 Sol 保留关键设计与最终集成，Luna 取证角色回答边界明确的只读问题，Terra code-executor 负责目标明确但仍需连续读取、运行和修正判断的代码目标，Luna worker-luna 承担结果含义、做法、边界和验收已经明确的主要执行工作。Spark worker 承担相同合同，在有限额度可用而且极快输出能明显缩短等待时选择。执行责任可以是代码修改，也可以是文件处理、命令批次、构建、测试、脚本或步骤明确的工具操作。执行边界由剩余判断负担决定，不由任务是不是代码、文件数或工作量决定。Terra 已经固定诊断和结果语义时，可以把独立执行或验证单元交给相应执行者，但 Terra 仍拥有整个代码目标并负责整合和验收。
- 实验依据：2026-08-01 代码 A/B 中，单 explorer 加证据账本将时间从 454.637 秒降到 303.395 秒，输入 token 从 1,004,927 降到 552,747；但只读路线没有建立临时测试环境，动态确认弱于主任务直查。
- 补充实验：同一基准仓库中，Spark 接收“只修复深层配置合并”合同后正确完成补丁、输入不变和生产配置断言；让 Spark 独立诊断整个仓库时虽然找到多项明显错误，却漏掉安装路径、第二次 matcher 参数、并行实现、jobs 默认值、reporter 开关和文档参数等跨文件问题。速度和高思考档不能替代任务所需的整体判断能力。
- 多文件合同测试：2026-08-02，Spark 在不修改验收文件的条件下同时完成深层配置合并、pipeline 调用修复、orchestrator 参数接线和 CLI 文档更新，基线 5 项错误全部转为通过。它没有修改已经正确透传参数的 `cli.py`。这支持按剩余判断负担而非代码行数划分 worker；该单次合成测试不证明 Spark 适合开放式诊断，也没有比较总费用。
- 连续执行者测试：2026-08-02，Terra High 直接从主任务接收同一个多文件工作包，独立完成读取、修改和动态验证；验收文件未改，5 项验收、模块帮助命令和实际 CLI 运行均通过。它还主动修正了 CLI 帮助与使用文档。外层测试在 184 秒后失去输出，最后一次测试活动约在启动后 204 秒，因此只能确认实现质量，不能把低首字延迟当作低完成延迟，也不能确认正常交回时间。该结果支持保留 Terra 与 Spark 两条同级路线：剩余判断较多时选 Terra，合同已经清楚时选 Spark，不建立固定接力。
- 大型机械任务测试：2026-08-03，Spark worker 从结构化工作簿生成六张表、123 个字段、23 个单选和九个关联的飞书 schema，绝大多数转换和本地验收正确，说明工作量和文件数量不应成为 worker 的硬限制。它把“创建人改为 `created_by`”理解为改字段名而不是改字段类型，并漏掉一个双向关联的反向字段名；主任务在外部写入前的局部抽查发现并修正。该结果支持把 worker 的边界定义为“结果语义已经确定”，并要求合同用目标、上下文、交付与验收、边界明确会改变结果的不变量，而不是把任务机械限制为小补丁。
- 配置原则：Root Base 只给主任务。由于当前运行时忽略 agent TOML 中的 `model_instructions_file`，全局继承层只加载中性 Base；Root Base 由全局 `developer_instructions` 加载，Worker Base 镜像在八个执行角色实际生效的 `developer_instructions` 开头，两个阶段角色分别维护完整的专属提示词。所有角色共同需要的平台、安全、证据和验证底线放在全局 `AGENTS.md`，领域方法放 Skill，角色专属证据方式和工具边界留在各 TOML。这样不会让下级继承用户沟通、整体路由和产品判断；共同 Base 源文件与运行镜像通过静态一致性检查防止漂移。
- 当前路由调整：历史 Spark 实验继续证明固定合同执行者的能力边界，但 Spark 的独立额度有限，不再据此把它设为主要执行者。worker-luna 作为常规执行者，Spark worker 只保留额度可用且速度收益明显时的路线。
- 前向加载验证：2026-08-03 新持久会话的主任务实际加载了“目标、上下文、交付与验收、边界”和“工作量、文件数量不是 worker 限制”的规则；唯一 worker 子会话实际加载了“语义完整、可独立验收”、工作量规则和精简 PowerShell 规则。测试使用一次 `fork_turns: "none"` 委派和一次长等待，worker 正确读取唯一事实来源并结束，没有重新派活。
- 规则编辑失败：2026-08-06，主任务用最近三轮对话委派 worker 扩展自己的职责，并明确不新增 Luna Low 角色。worker 第一次选择了工作区中的旧副本而非全局生效文件；补充真实路径后，它又擅自新增 `quick-worker`。这说明有限 fork 可以传递原始讨论，却不能替代权威文件、当前责任和最终边界；也说明提示词和长期规则的语义不能交给执行型 worker 自行形成。当前规则由掌握用户目标的负责人撰写，worker 只在最终文字或准确改法已经确定后承担机械同步。
- 失败信号：报告把静态可疑点写成已验证；主任务收到报告后才发现关键测试从未运行；同一诊断被 explorer 和主任务完整做两遍。

## R11 中心汇总和稀疏通信

- 问题：自由通信容易把协调本身变成主要工作，并让错误在代理之间扩散；完全禁止通信又会保留已知依赖和重复工作。
- 理由：默认 hub-and-spoke 让主任务拥有最终判断；只有明确依赖、冲突或重叠时才发送定向消息。Google 实验中集中式架构对独立错误的放大低于无中心结构，但中心编排本身仍有通信开销。
- 来源：https://arxiv.org/html/2512.08296v3
- 失败信号：代理互相发送没有问题或行动要求的状态消息；多个代理因为不知道对方边界而重复搜索；主任务失去最终证据链。

## R12 验收就绪即停止

- 问题：把“进程自然结束”当成唯一完成信号，会为可选扩展和慢分支支付尾部延迟；把中间消息当完成又会导致漏项。
- 理由：委派的完成条件定义验收就绪。必要路线达到条件后整合，可选扩展停止；每次追加工作必须对应一个仍会改变结果的未决问题。
- 依据：Anthropic 公开复盘把长时间同步等待和不断扩展搜索列为实际失败模式；Codex 原生多 Agent 提供定向消息、中断、等待和显式关闭能力。
- 来源：https://www.anthropic.com/engineering/multi-agent-research-system
- 来源：https://github.com/openai/codex/tree/bf9fd885b2546e91fe3bab271aa481b070f47518/codex-rs/core/src/tools/handlers/multi_agents
- 失败信号：核心答案已经满足却继续等待旁支；只收到进度消息就提前交付；没有新问题仍重复调用工具。

## R13 等待时挂起主任务

- 问题：subagent 工作期间用短轮询反复恢复主任务，会重复装载 Sol 上下文、生成没有新信息的进度，并增加等待成本；subagent 用定向消息提前发送普通结果后继续运行，同样会唤醒上级并产生重复整合；主体完成后为一句文案等小事再次交接，还会增加尾部延迟。
- 理由：启动执行者后，“其他独立工作”只指执行者合同之外、无论它返回什么都仍然必要的责任。存在这种责任时，当前负责人继续推进，到第一个汇合点再等待；没有时就用一次可中断的长等待挂起。每个下级完成时先接收并处理新结果，不必为了等齐而闲置已经释放的执行能力；只有当前工作依赖仍在运行的必要下级时才继续长等待。新结果产生一个会改变答案、仍在原范围内且不依赖其他路线的具体缺口时，可以继续使用已经完成并熟悉相关上下文的执行者；没有真实缺口时不为保持并发而派活。宿主负责显示状态和确定性心跳，执行者只在完成、受阻或需要决定时交回；用户新消息可以中断等待。并行任务拥有不同责任或文件范围。执行者交回后只做会改变结论的定向验收，由阶段所有者完成其合同内的小收尾。
- 实验依据：2026-08-02 原生路由测试中，Terra High 主体工作 404.026 秒、首 token 3.197 秒；Sol 会话总计 593.052 秒，并因多次短等待累计 821,103 input tokens，其中 743,936 为 cached input。主体完成后为 README 一句说明重新唤醒 Terra，又增加 18.263 秒和一次交接。隐藏验收最终为 10/10，说明减少等待轮次和小收尾交接不会要求降低结果标准。
- 测试限制：使用 `codex exec --ephemeral` 时，subagent 完成钩子无法找到父 transcript，造成交回异常。测试原生 subagent 必须保留父会话；这个限制属于测试装置，不应误判为模型失败。
- 前向验证：2026-08-02 新持久会话中，主任务启动 code-executor 后先独立读取 `CONTRACT.md` 并形成验收清单，在第一个依赖点只调用一次 3,600 秒可中断等待；执行者 21.855 秒完成，主任务随后只运行一次最终验收，没有轮询或重新唤醒。测试同时发现一次无效调用：主任务先把指定 `code-executor` 与 `fork_turns: "all"` 组合，宿主拒绝后才用 `none` 成功。当前修正是由创建者先写任务合同并与最近对话比较：合同已经承载结果相关信息时使用 `none`，仍有难以安全概括的信息只存在于最近对话时传最少有限轮数；命名角色保留自己的模型配置。
- 修正规则后的复验：新会话首次即以 `fork_turns: "none"` 创建唯一 code-executor；主任务在其运行时只读契约，到汇合点调用一次长等待。执行者 31.770 秒完成，首 token 2.960 秒；主任务没有发送额外消息或重新派活，只运行一次正式验收后结束。测试目录中只有 `processor.py` 的修改时间发生变化。
- 新验证：2026-08-04 的 Luna explorer 在任务完成前用 `send_message` 发送结论，根任务的长等待因此提前返回；explorer 随后继续读取、补充消息并等待上级，直到被中断仍未结束。完成应通过最终回答一次性交回并结束；定向消息只留给运行中需要上级立即决定的真实阻塞或范围、权限、公共架构变化。
- 失败信号：主任务每隔几十秒恢复但没有新信息；明明还有独立工作却立即等待；主任务和后台执行者重复调查或同时写同一状态；交付依赖后台结果却没有在结束前接收；执行者发送例行状态或普通结果后继续运行；没有下级任务却等待上级回复；完整结果交回后重新派回一句文案或格式调整；指定角色先用 `all` 失败再重试；ephemeral 父会话下测试原生 subagent。

## R14 发现召回与证据核验分离

- 问题：开放式搜索中，某条路线没有返回候选，只能证明它没有找到，不能证明候选不存在。若主任务把内部完整的证据表当成全局覆盖证明，会得到精确但严重漏项的答案。
- 理由：发现阶段优化召回率，应优先使用能枚举来源的确定性检索底座；没有这种底座时才依赖覆盖矩阵、不同入口和关键接缝处的受控冗余。核验阶段优化准确率，再给候选设唯一所有者。主任务检查覆盖记录和异常空白，不必重新宽泛搜索。
- 实验依据：2026-08-01 半导体新闻对照中，两路编排耗时 317.205 秒、输入 669,861 token，单任务直搜耗时 661.817 秒、输入 6,936,013 token；但两路编排只返回 2 条新闻，直搜返回 8 条。缺失的 6 条均属于已经委派的范围，说明失败发生在候选发现，而非证据交接或去重。
- 依据：Anthropic 的公开复盘要求先宽后窄，并让 lead agent 根据已得结果继续派生调查；它同时强调子代理任务要有清楚边界，而不是宣称互斥分区天然具有完整召回。
- 来源：https://www.anthropic.com/engineering/multi-agent-research-system
- 失败信号：某一大类意外为空却没有覆盖记录；最终使用“没有找到”推导“没有发生”；为了零重复让每个入口只由一个搜索者检查；核验很精确但结果数量明显不足。
- 后续复验：v3 把三条高收益路线前置并禁止下级派生，耗时降到 570.682 秒、输入 1,240,333 token，实际线程数与计划一致；但只返回 4 条，并遗漏基线已取得正式材料的 MPS、Cohu、AXT 和 MediaTek。说明提示词覆盖矩阵能控制组织开销，仍不能让模型搜索稳定替代确定性候选枚举。
- 确定性入口原型：通用 `search-source-registry` 的半导体新闻来源包在 5.8 秒内通过 SEC EDGAR 枚举 24 家公司的 4,905 条相关表单记录，并在固定时间窗产生 8 个候选，直接找回此前漏掉的 MPS、Cohu、AXT 和 Amazon。新建的 Luna web-researcher 能自行加载 Skill 并复现相同结果，主任务无需读取来源表或脚本。TDK 直连返回 403、Cohu 页面超时仍被记录为未覆盖，说明来源注册表必须保存失败状态，不能只保存候选。代码研究另有按 API、版本、Bug、依赖、安全和标准划分的官方来源表；它与半导体入口共用“先选原始来源、再枚举和核验、明确覆盖缺口”的方法，不强行共用同一种程序。

## R15 受控的第二层执行

- 问题：完全禁止 subagent 创建下级代理，会让已经拥有阶段上下文的 Luna 或 Terra 在发现一个明确下一步后先把结果交回 Sol，再由 Sol 重新读取主上下文、编写委派和等待；允许自由派生则会隐藏真实工作量、制造重复路线和无结果线程。
- 理由：最大深度限制为两层，只给 `probe`、`research-lead` 和 `code-executor` 开放受控派发。下级工作必须边界清楚、可独立验收、无需新的用户或关键判断；父代理继续拥有整个阶段，负责等待、整合、验证和普通修正。第二层把结果交回创建它的上级，不越过阶段负责人直接要求根任务处理；阶段负责人只把完成结果、真实阻塞或需要更高层决定的问题继续上交。`explorer`、`web-researcher`、`worker` 和第二层代理不再创建代理。这样减少 Sol 的中间恢复，同时保留明确的责任和停止条件。
- 适用情况：probe 探查后只剩一个明确步骤；完整研究阶段存在两个以上互不重叠的来源方向，由 `research-lead` 创建搜索工人；code-executor 已固定诊断和结果语义后需要一个机械实现或独立验证单元。其他情况直接完成或交回上级。
- 反面实验：搜索 v2 中，主任务计划使用 4 个 web-researcher，但系统实际创建 6 个线程；一个定向代理创建两个下级线程后立即停止，没有形成报告。该版本产生 40 个协作工具事件，耗时 700.251 秒，慢于 661.817 秒的单 Agent 基线。这证明自由派生和父代理提前结束有害，不证明带所有权和验收条件的一层派发必然有害。
- 新证据：2026-08-03 对 24 个近期 Sol 根任务的审计记录到约 3,360 个推理片段和 334M 输入 token，其中约 96.3% 为缓存输入；使用 subagent 的任务有 172 次无新信息的等待超时，但两个高成本任务的主要消耗来自 Sol 自己逐步驱动数百次工具调用。只修等待不足以解决问题，还需要让便宜的阶段负责人保留下一步所有权。
- 质量边界：此前搜索 v2 还把北京时间 16:00 发布的 Comet 公告纳入截至 15:20 的窗口，说明父代理的覆盖整合不能代替硬条件 gate；阶段负责人必须在交回前执行明确的时间、范围和验收检查。
- 失败信号：下级线程未形成可验收结果；父代理创建下级后立即结束；实际委派数超过合同；下级路线重叠或同时修改共享状态；普通中间结果仍逐级返回 Sol；第二层代理继续派生。
- 首次前向测试：2026-08-03，Sol 以 `fork_turns: "none"` 创建 probe 并进入长等待；probe 获得了第二层 `spawn_agent`，随后把指定 `worker` 与 `fork_turns: "all"` 组合，宿主拒绝后又等待未创建的任务，导致外层测试 10 分钟超时且没有生成结果文件。这证明深度和工具已经生效，也说明阶段负责人需要自己的创建规则：先写合同，由创建者比较合同与最近对话，再选择 `none` 或最少有限轮数；命名角色保留自己的模型配置；确认创建成功后才进入等待。
- 修正后的嵌套验收：2026-08-03，新会话形成 `/root → probe → worker` 两层结构。probe 使用自包含委派，worker 从唯一事实文件计算结果并写入 `RESULT.txt`，probe 自己核验内容后交回；总耗时 54.9 秒，结果严格为 `17`，主任务没有读取事实文件或代替下级写入。这证明受控第二层能够在原生 subagent 中实际运行，并让阶段负责人保留执行上下文和验收责任。
- Deep Research 结构验收：2026-08-03，新会话形成 `/root → research-lead → 2 个 web-researcher`。Luna High 的 research-lead 划分两个独立官方来源方向，搜索工人分别取证，lead 处理覆盖、冲突和综合，Sol 没有重新联网搜索；最终两个事实均有官方直接链接和限制说明，结构与质量验收通过。该任务只用于验证组织结构，规模太小，不能作为成本或速度优于 Sol 直做的对照结论。
- 等待缺陷：同一次研究测试中，research-lead 使用 12 次等待和多次代理列表检查，其中两次等待参数低于宿主最小值；它还在自身阶段完成前向 Sol 发送消息，导致 Sol 提前恢复并追加等待。早期修正又把流程写得过于接近“发出一批任务，等全部收齐”，可能在一个慢分支运行时闲置已经完成的搜索工人。当前规则改为：搜索工人不发例行进度；lead 在每个结果到达时立即整合，只有当前工作依赖仍在运行的必要路线时才长等待；新结果出现真实、独立且仍在原范围内的缺口时优先继续使用熟悉该材料的已完成工人；没有缺口时不为保持并发而派活；完成综合后只向上级交回一次。该动态调度修正尚未进行完整联网对照。

## R16 模型与程序的责任边界

- 问题：候选程序、来源表或覆盖字段容易被误当成研究者，使机械查询成功被写成结果充分，随后又用更多启发式规则修补语义判断。
- 理由：模型负责理解用户目标、选择查询和来源、判断相关性与充分性、处理冲突并形成结论。程序适合承担可重复的抓取、过滤、去重、重试、限额和记录；它可以执行透明的机械补搜，但不能判断候选是否成熟、搜索是否完整或项目是否应当采用。
- 实验证据：同一 Python 重试库任务中，自然语言查询的 GitHub 请求成功但返回零候选；机械 `OR` 补搜恢复了 `tenacity` 等候选，同时混入无关高星项目。说明程序能够修复确定的召回故障，相关性和后续路线仍必须由模型判断。
- 失败信号：把接口返回成功写成研究成功；根据候选数量宣布完整；不断把语义判断编码成停用词、阈值和评分；模型不检查程序输出就直接给出采用结论。

## R17 命名角色，不设置 default

- 问题：全局 `default_subagent_model` 会在命名角色的配置文件加载前参与创建校验。它设为 Luna 时，即使 `spawn_agent` 没有传 `model`，当前宿主仍会先按 Luna 校验并拒绝创建；`default` 还可能继承主任务的模型、思考强度和无关上下文。
- 规则：全局不设置默认 subagent 模型。自动委派只使用职责匹配的命名角色，每个专用角色从自己的 TOML 取得模型和思考强度。`default` 只保留为宿主兼容叶子入口，显式读取工人 Base、禁止派生，不作为自动路由的兜底。没有贴合角色时由当前负责人处理。
- 配置细节：`explorer`、`web-researcher` 和 `browser-operator` 在自己的配置中选择 Luna Medium，`worker-luna` 选择 Luna Low，`research-lead` 选择 Terra High，`code-executor` 选择 Terra High，`worker` 选择 Spark High。调用命名角色时不传模型覆盖。创建失败时保持原责任，不通过改换角色来绕过。
- 实际证据：2026-08-04 的任务 `019fca6d-39d5-7673-842f-64669197019e` 共记录约 108.57M 输入 token，其中根 Sol 和三个 `default` Sol 子任务合计约 90.66M，占 83.5%；四个 Luna 子任务合计约 8.06M。浏览器子任务 `inspect_feishu_view_plugin_access` 创建时明确选择 `agent_type: "default"`，实际运行模型为 Sol xhigh；它持续 15 个回合，记录 363 个模型用量片段、102 次等待和约 49.80M 输入，单独超过根 Sol 的 37.82M。三个 default 子任务合计约 52.84M Sol 输入。
- 历史验证：2026-08-04 的验收任务 `019fcba1-1f96-7503-ad05-5d492ee7615c` 曾确认显式配置的 `default` 可以运行成 Luna High；同日后续任务又确认全局 Luna 默认值会在命名角色创建前触发模型白名单拒绝。现行配置继续删除全局默认模型；后来恢复的 `default` 只作为兼容叶子入口，不改变专用命名角色路由。
- 修复验证：删除全局默认值和 `default` 入口后，主任务以 `agent_type: "explorer"`、`fork_turns: "none"` 且不传 `model` 创建子任务 `019fcce7-010d-7960-a062-ff44dd1565e7`。它第一次启动成功，实际运行 `gpt-5.6-luna`、High，并完成配置核验；主任务只创建一次并使用一次长等待，没有改派 Terra 或重复读取相同文件。

- 失败信号：创建命名角色时仍从全局默认值取得模型；已有命名角色却改用 `default`；角色启动失败后把只读调查改派成代码执行任务；名义上大量使用 Luna，实际用量仍由 Sol 占多数。
- 没有采用的路线：在每个会话的 `SessionStart` hook 中无条件创建一个助手。任务出现前无法给出有用合同；空助手会固定占用并发槽，完整继承又会带入无关上下文。Codex 当前只执行 command hook，`agent` hook 会被跳过，因此 hook 也不能直接创建受当前主任务管理的原生 subagent。

## R18 减少高价主任务的重复唤醒

- 问题：便宜的 subagent 已经承担部分工作时，根 Sol 仍可能亲自完成大量工具调用、逐步驱动下级、反复等待和处理每个中间结果。长会话还会让同一批历史在每次 Sol 调用中重新进入输入。此时 subagent 本身很便宜，整棵任务树的成本仍由根 Sol 决定。
- CC Switch 证据：2026-08-03 至 2026-08-04 的 Codex 请求日志中，Sol 共 1,838 次调用，估算成本 181.5369 美元；Luna 共 712 次调用，估算成本 1.6203 美元；Terra 共 148 次调用，估算成本 4.5778 美元；Spark 共 587 次调用，估算成本 9.5028 美元。每条日志都有唯一 `request_id`，因此这些记录是独立调用，不是同一累计快照的重复行。
- 短调用放大：Sol 有 929 次调用的输出不超过 256 token，占 Sol 调用的 50.5%，估算成本合计 74.7955 美元，占 Sol 成本的 41.2%。这些调用平均仍携带约 12–14 万输入 token，说明短工具决定、等待恢复和局部确认也会反复付出长上下文成本。
- 最近任务复核：排除长期讨论任务 `019fb761-4bea-7d91-8edc-8dfa5ed3832b` 后，最近 48 小时仍有明显的主任务工具往返。浏览器检查任务 `019fca96-480a-7e93-bbfc-e874166b9ced` 记录 301 次 Sol 请求和 213 次 MCP 工具完成，估算成本 27.4517 美元；任务 `019fcbf1-438a-7231-99f1-0450a30ec872` 只有 11 条用户消息，但记录 329 次 Sol 请求和 63 次 MCP 工具完成，估算成本 32.8236 美元。它们说明日常任务中的主要可减成本不只来自长对话，还来自主任务在第一批结果之后继续逐轮读取、操作和检查。
- 任务树证据：任务 `019fca6d-39d5-7673-842f-64669197019e` 整棵树估算 65.0156 美元，其中根 Sol 为 30.7265 美元，一个误路由到 Sol 的 `default` 子任务为 27.4517 美元；同一任务树中的 138 次 Luna 调用合计约 0.2663 美元。根任务记录了 78 次 `wait_agent`、24 次 `followup_task`、18 次 `list_agents`、14 次 `send_message` 和 18 次 `spawn_agent`；Sol default 子任务又记录了 239 次执行调用和 102 次等待。
- 正向对照：研究结构测试 `019fc72a-6470-76a0-a50a-186db5423ae6` 中，根 Sol 只调用一次，research-lead 与两个 web-researcher 共 14 次 Luna 调用，Luna 部分估算约 0.0253 美元。探针结构测试 `019fc728-cc5d-7822-a7a3-890e0edad24e` 同样只使用一次根 Sol 调用，后续由 Luna probe 和 Spark worker 完成。它们规模较小，只证明阶段所有权能够实际减少根任务恢复次数，不单独证明所有大型任务都会更快或更便宜。
- 新失败测试：2026-08-04 的中等规模只读代码调查 `019fccc2-522c-7012-880d-0e7ef6318bae` 自动决定委派，但根任务在下级运行时又读取同一批源码、文档、schema 和 SDK，并自行重建结论。根 rollout 记录 15 次模型用量更新，最终累计 889,225 input token，其中 794,880 为 cached input；下级记录 8 次更新和 173,125 input token。根任务还先后尝试 `explorer`、`code-executor` 和显式 Terra：当时的全局 Luna 默认值在命名角色配置加载前触发白名单拒绝，随后根任务又错误地把只读责任改成代码执行角色。这个测试同时暴露了阶段所有权、角色保持和默认模型校验三个问题。即时 CC Switch 快照只显示少量请求，完成后的 rollout 才显示全部调用，因此测试以任务结束后的模型用量为准；默认模型问题后来已按 R17 修复并完成前向验证。
- 对 subagent 规则的影响：无需工具或一次工具批次只返回少量内容即可完成的工作由当前负责人直接做；连续多轮探索或单步就要处理大量材料时，把完整过程交给职责匹配的低成本命名角色。原本预计一次工具批次可以完成，但第一批结果表明仍需继续读取、浏览器操作、代码诊断或状态检查时，当前负责人重新判断剩余阶段；关键判断不要求它亲自接触这些证据时，把剩余阶段完整交给合适角色，不再继续逐轮调用工具。委派发生后，下级拥有合同内全部下一步，上级只做合同外且无论下级结果如何都仍然必要的责任；没有时直接长等待。角色启动失败只修正一次无语义影响的参数，不能通过改变角色职责来绕过。Subagent 完成后一次性交回并结束，普通过程和长日志留在自身任务中；上级只针对具体矛盾、缺口或高风险事实验收。
- 共同规则入口：全局 `~/.codex/AGENTS.md` 只承载所有角色都需要的平台、安全、证据、成品、验证和最小责任链；工人合同与阶段所有权分别由两份 subagent Base 源文件定义，并镜像到对应角色的 `developer_instructions`。当前版本的角色覆盖白名单不接收 `project_doc_max_bytes`，所以 agent TOML 中的这一项不会按角色关闭项目 `AGENTS.md`；所有角色仍读取会话实际加载的全局和项目规则。没有使用 `SubagentStart` hook，因此不需要额外命令、信任状态或常驻同步脚本；如果以后创建全局 `AGENTS.override.md`，需要把共同规则一并迁移，因为同层 override 会取代 `AGENTS.md`。
- 对通用工作原则的影响：当前负责人把同一判断所需、彼此独立且输出有界的读取与验证合并成一次工具批次。Root Base、两份 subagent Base、角色专属提示词和全局 `AGENTS.md` 按实际阅读者装配；执行型 subagent 不继承 Root Base。长任务把仍影响行动的状态写入稳定入口，目标实质切换后再建议从新任务继续。
- 边界：前一步结果会改变下一步时保持分轮执行；关键判断和高风险验收仍由合适的强模型负责；同一目标内的连续工作不为降低调用数而强行拆成新任务。
- 后续验证：按任务树比较根 Sol 调用次数和成本、各模型成本占比、不超过 256 输出 token 的 Sol 调用比例、等待与代理管理调用次数，以及结果正确性和完成时间。只有这些指标和结果质量同时改善，才认为规则有效。

## 当前验证要求

先用真实任务观察以下指标，不预先增加更多规则：

- 结果是否正确、完整并符合用户用途；
- 日常辅助是否减少主任务的低价值读取和工具等待；
- 是否出现重复工作、无意义交接或固定探针；
- 高耦合任务是否保持连续主干；
- 关键证据是否能够到达最终判断者；
- 成本和耗时增加是否来自完成任务所需工作，而不是组织开销。

每次改动至少检查三类行为：

- 应当委派：一个边界清楚但需要连续多轮读取的本地调查交给 `explorer` 后，根任务不再读取同一材料，只等待并采用结果。
- 容易混淆：`code-executor` 把一个确定实现交给 `worker` 后，只继续 worker 合同外仍然必要的代码目标；诊断、整合和完整测试仍由 `code-executor` 拥有。
- 不应委派：无需工具或一次工具批次只返回少量内容就能完成的检查由当前负责人直接做；高风险关键判断由主任务读取会改变结论的原始证据。

## R20 根据上下文价值复用线程

- **目标：** 让同一任务既能利用 subagent 已经形成的理解，又能在无关工作中获得干净上下文；线程额度服务于这项选择，而不是成为并行数量目标。
- **原有状态：** 委派规则已经要求顺序依赖、共享状态和连续理解由同一执行者持续负责，但实际派发仍通常为每项新责任创建新线程。运行时上限为 6 时，这种做法很快耗尽线程名额。
- **问题或新证据：** Codex Desktop `0.147.0-alpha.6.6` 的真实探针中，六个 subagent 完成后，第七个新线程仍返回 `agent thread limit reached`；对完成线程调用 `interrupt_agent` 也不释放名额。使用 `followup_task` 重新启动 `probe_01` 则成功，1.316 秒内返回 `recycled`。同时，用户指出不同阶段负责人都可能连续派发大量琐碎、同类、无需重新判断的工作；若把复用写成 worker 特例，就要在多个有委派权限的角色中分别维护同义规则，也会让模型误以为复用取决于角色名称。
- **形成的理解：** 是否复用不应按角色名或“新任务”三个字机械决定，而应看旧上下文对下一责任是资产还是干扰。同一问题、代码状态、来源路线或执行流程中的后续工作受益于连续理解；无关判断需要隔离。同一种做法继续应用到更多对象，而且目标、边界和验收不变时适合复用；需要重新判断含义、方案或边界时适合隔离。角色名称不决定复用，因而所有有委派权限的负责人可以使用同一原则。
- **实际修改：** Base 与子代理共享委派规则增加复用判断：有用则通过 `followup_task` 延续，无关或可能污染判断则新建干净线程；连续责任只是在更多对象上重复已确定做法时复用原执行者，需要重新判断时新建代理。Codex 的公开线程上限提高到 32，并移除旧 `features.multi_agent_v2` 中的专用值 7，避免它覆盖公开字段。
- **保留边界：** 仍按依赖、所有权和净收益决定并行，不把 32 个线程当作并行目标；复用不能把无关责任塞给带有旧假设的代理；阶段负责人继续拥有整合和验收，执行者不因被复用而获得合同之外的判断职责。
- **否决或缩小的路线：** 没有把所有任务都固定复用六个持久代理，因为无关上下文会污染判断；也没有仅把上限无限提高，因为这不能表达何时应利用已有理解，并会弱化成本和并行控制。
- **验证状态：** `followup_task` 复用已由真实新任务验证；全局配置、Base 和共享规则已写入并完成结构同步。32 线程配置已由新任务确认加载为包含 Root 的 33 个总槽位；长期调度效果需要在真实开发和研究任务中观察。
- **证据：** 探针任务 `019ff6bb-8240-7a73-9fbf-4f5cbe399842`；修改前备份 `prompt-lab/backups/before-subagent-context-reuse-20260813-002613/`；相关上游问题为 openai/codex#22779、#32353。
## R21 浏览器阶段由专业角色连续拥有

- **目标：** 任务确实需要页面交互或真实界面状态时，让低成本的专业角色连续承担浏览器阶段；上级保留目标、权限、结果和后续判断，不被每次点击、等待和页面变化反复唤醒。
- **原有状态：** 系统已经区分 Codex 内置浏览器与 Chrome，也曾要求同一个 `browser-operator` 连续操作页面，但没有明确要求创建 subagent，工具选择、证据要求、阶段所有权和替代路线又混在同一句规则中。
- **问题或新证据：** “由同一个 browser-operator 完成”仍可能被 Root 理解成自己使用浏览器工具；上级也可能创建下级后继续逐步指挥或亲自接管。2026-08-04 的浏览器任务中，一个误用 `default` 的 Sol 子任务持续 15 个回合、363 个模型用量片段和 102 次等待，约 49.80M 输入 token；同一根任务还出现大量 `wait_agent`、`list_agents`、`followup_task` 和 `send_message`，逐步协调不断重放上下文。
- **形成的理解：** 浏览器操控天然需要多轮读取可见状态、点击、等待和处理页面变化。接口、CLI、文件或专用连接器能够直接取得结果时，这些路径通常更快，也不需要反复恢复模型。任务需要浏览器时，操作成本无法靠缩短合同消失，应通过专业角色和完整阶段所有权隔离。直接读取可以支持网络取证，但不能单独证明用户实际看到的页面或界面流程。
- **当前规则：** 能够通过接口、CLI、文件或专用连接器直接取得结果时优先使用这些路径。任务需要浏览器时，主 agent 或有调度权的阶段负责人创建 Luna Medium `browser-operator`，用完整任务合同把整个浏览器操作阶段交给它连续完成。主任务和其他角色不自行操作或接管同一阶段。浏览器的选择和真实页面验证由 `browser-operator` 负责。Computer Use 和浏览器之外的 Windows 应用操控保留给 Root。
- **共享规则归属：** 浏览器选择和页面证据只由 `browser-operator` 读取；创建、委派和阶段所有权只由 `research-lead`、`code-executor` 等有调度权的负责人读取。不能创建下级的直接执行角色不再加载这些规则。
- **保留边界：** 浏览器操作不会扩大用户授权。查看、填写、发送、发布、购买、删除、权限变化和不可逆提交仍按任务合同与用户授权判断。普通页面变化和局部重试由 `browser-operator` 在阶段内处理；需要新的产品、架构、权限或任务范围决定时交回上级。
- **失败信号：** Root 或阶段负责人亲自执行连续页面操作；上级逐次发送点击指令；同一浏览器阶段在多个执行者之间切换；只凭服务器端或 DOM 结果宣称真实界面已经验证；没有真实页面要求却为了形式启动浏览器。
- **验证状态：** Base、共享源、角色注册和有调度权的阶段负责人已经同步为完整浏览器操作阶段所有权。尚需在新的真实浏览器任务中验证 Root 和其他角色不会自行操作或接管浏览器，并由 `browser-operator` 选择正确浏览器和交回可核验证据。
- **证据：** 任务 `019fca6d-39d5-7673-842f-64669197019e`、`019fcbf1-438a-7231-99f1-0450a30ec872`；修改前备份 `before-capability-scoped-shared-rules-20260813-011950`；多代理提示词体系演变记录阶段十四。

## R22 委派后直接等待，不另建调度循环

- **目标：** Root 掌握整体任务路径并根据陆续返回的报告继续调度，但已经交出的阶段不再由 Root 重复执行；高价主任务没有报告或新责任可处理时直接挂起。
- **原有状态：** 会话前成熟 Base 依次规定“每项责任只有一个所有者”“完整阶段交给 subagent 后由它连续负责”“调用 `wait_agent` 等待”和“报告完整可信时直接采用”。后来的框架重构把这些直接动作改写成独立的“调度循环”，加入“先获取关键事实”“继续尚未分配且不重叠的工作”“整合和验收”等抽象判断。
- **问题或新证据：** 任务 `019ff71f-3348-78d0-befa-32eaea1a1436` 已加载当时的最新 Base，但 Root 创建 `web-researcher` 查找 GPT-5.6 官方提示词后，仍亲自进行网页搜索、GitHub 搜索、克隆仓库、提取模板和计算哈希；翻译 worker 返回后，Root 又阅读全文、比较结构、修改译文和重复验证，随后才创建独立审校代理。Root 把同一阶段重新解释成“核验关键事实”“整合”或“验收”，说明“不重叠”仍依赖模型自行命名责任。
- **形成的理解：** `wait_agent` 本身会在任一 subagent 发来消息或完成时唤醒上级；处理报告、派发后续、没有新工作时再次等待，已经自然形成调度过程，不需要额外描述一套循环。有效约束是明确动作顺序：完整阶段交出后由下级连续负责，上级停止该阶段，没有其他责任可派发时直接等待。委派判断同时看模型往返和进入当前上下文的材料量；即使只有一次工具调用，只要会带入大量材料、命令输出或页面内容，也可能适合完整交给低成本角色。
- **实际修改：** Root Base 恢复每项结果的单一负责人和阶段负责人的完整所有权。阶段负责人连续掌握合同划定的阶段或模块，负责核心工作、阶段内辅助责任、整合、验证和收尾。Root 处理尚未分配的责任、跨阶段衔接和最终整合。Base 与阶段负责人提示词删除“异步推进”和“任一报告返回后立即处理”的指示，只保留下一步确实依赖仍在运行的下属时才等待。角色注册描述恢复“完整负责一个已划定阶段或模块”的定位。
- **保留边界：** 无需工具或一次输出有界的工具批次仍可由当前负责人直接完成。互不依赖的责任仍可并行。worker-luna 仍是做法和验收已经明确时的主要执行者。高风险事实、具体矛盾和会改变结论的证据缺口仍可由合适的强模型定向核验。
- **否决或缩小的路线：** 不规定固定 agent 数量，不增加一套异步调度循环，也不单独写“Root 不得安排阶段下属”。正面写清阶段所有权和 Root 的剩余责任。
- **验证状态：** 当前版本已完成文字和静态同步。仍需用新的真实多代理任务验证 Root 只管理阶段负责人，并减少等待、列表检查和直接叶子派发。
- **证据：** 任务 `01a03d4e-3fd3-7040-b965-5b51eaa00fe0` 中 Root 直接创建 14 个 subagent 并执行 43 次 `wait_agent`。任务 `01a03d5a-6123-7de0-a29c-0db94e048cee` 中 Root 直接创建 21 个 subagent 并执行 57 次 `wait_agent`。两项任务启动时均实际加载“任一报告返回后处理”的 Base。旧版责任结构见提交 `25ed495`、备份 `before-agent-prompt-structure-20260825` 和 `codex_base_instruction_5.6.before-root-framework-refactor-20260811-195802.md`。

## R23 从极简骨架开始，按失败恢复功能块

- **目标：** 降低多代理提示词的维护和模型迁移成本，让新模型先用通用骨架展示自身能力，只恢复它仍然需要的规则块。
- **原有状态：** 当前架构由多轮真实任务逐步形成，规则已经较成熟；过去的精简主要从完整版逐句或逐段删除，再检查能否保持行为。
- **问题或新证据：** 逐句消融需要大量测试，相关句子被拆开后也难以定位退化原因。模型或宿主升级时完整迁移旧补丁，会让已经由新能力覆盖的说明继续进入上下文。
- **形成的理解：** 骨架负责角色目标、用途、正确完整可用的结果、硬边界和少量普遍行动；固定模块保存平台、环境、权限和难以靠普通行为样本安全删除的规则；每个功能块解决一个稳定缺口，并能独立加入、移除和测试。测试和恢复的单位是功能块，不是单句。
- **实际修改：** 冻结当前完整版作为恢复规则库，建立 `core-skeleton.md`、`module-map.md`、测试矩阵和候选 Base。候选保留固定模块，把多代理段压缩为七个方向，全文由 9858 字降至 9083 字。模型、宿主或工具变化时，从同一骨架重跑代表性场景，再逐块恢复。
- **保留边界：** 权限、安全、破坏性操作、平台机制和真实验证不会仅因样本未触发而删除。功能块仍按实际阅读角色装配；出现失败时优先恢复成熟旧块，不围绕单次输出增加新补丁。
- **验证状态：** 候选已由三个新 Root 任务和两个下级真实使用。小任务直接完成；大阶段任务直接创建两个不重叠 subagent，最终证据来自下级报告，未显示 Root 重新执行同阶段调查。本轮没有恢复功能块。动态工具载荷不可见，因此每次内部挂起是否调用 `wait_agent` 尚未直接验证。

## R24 极简的是各功能块，不是全局总纲

- **目标：** 保留完整的多代理功能面，同时让每个功能块从最短、具体、可执行的版本开始。
- **原有状态：** R23 正确确定了按功能块测试和恢复，但实施时又额外创建了只含目标、行动、结果和边界的四句全局骨架，并计划让新模型从它开始。

## R25 层级不改变证据强度，路线失效时及时回交

- **目标：** 让 Root 保持整体裁决和最终验收，同时让直接接触源码、原始资料、真实运行与用户可见结果的角色能够用证据纠正路线，避免所有角色在错误基础上继续返工。
- **原有状态：** 体系已经定义 Root、阶段负责人和执行角色的上下级关系、单一所有者和报告信任，但容易把“上级负责裁决”误读成“上级判断天然更可靠”，也没有把“用户结果不再支持路线”单独列为阶段负责人必须立即回交的条件。
- **问题或新证据：** 任务 `01a02db5-1a22-7ec0-bbba-d595d21837e0` 中，统计核心、原生 UI、发布物和评审在路线与 source of truth 尚未稳定时持续展开；局部测试通过后，独立审查才发现源码、发布物、说明和用户体验不一致，随后又在错误路线内多轮返工。任务 `01a02da1-3127-72c3-8479-31f5d8040592` 还显示角色注册、指令继承、工具暴露和运行时权限不能凭上级印象合并判断，必须分别取得真实证据。
- **形成的理解：** 层级决定谁组织工作、整合报告和作职责范围内的决定，不改变事实本身的强弱。下级不能以直接证据夺取整体任务，上级也不能因拥有裁决权而忽略或压低直接证据。用户结果已经削弱路线时，即使尚未形成明显冲突，阶段负责人也应及时交回证据和影响。
- **实际修改：** Base 和当前多代理规则加入“层级不改变证据强度”“直接证据必须被处理”“用户结果不再支持路线即回交”；`visual-usability-tester` 被限定为黑盒可用性证据角色，不获得审美、修复方案或整体交付裁决权。
- **保留边界：** Root 仍负责用户意图、整体路线、跨阶段和高风险判断、团队接口和最终验收；执行或取证角色仍只在合同范围内工作。不是鼓励角色互相反驳，而是要求证据通过既定责任链改变路线或合同。
- **验证状态：** 已完成 Base、角色配置、当前规则和功能块基线的静态同步；明确构建请求与只读诊断的独立前向测试通过。真实代码开发中阶段负责人能否在路线失效时及时回交，仍未验证。

## R26 新任务先重新理解现有项目，再处理被实际触发的风险

- **目标：** 新任务接续现有项目时，从当前项目重新建立整体理解，让用户不必重新记起并复述全部背景，也避免用理论安全、权限或边界问题替代项目理解。
- **问题或新证据：** 任务 `01a03e36-e2e8-7cc2-b9ce-a5fc5155b9c9` 在查明现有扩展的入口、场景块和角色召回机制之前，先扩展了证据账本、攻击性评审和多类理论风险，后来才发现新路线重复而且弱于现有主体流程。任务 `01a03e37-a76f-74d1-b640-555566c0c1ae` 先加载旧任务的大量原始工具输出，随后由主任务反复读取浏览器状态和等待，实际项目入口与低风险核验出现较晚。
- **形成的理解：** 新任务不能把旧会话摘要当作当前项目本身，也不能要求用户重新提供能够查明的背景。模型先从当前项目重新建立理解，旧会话用于恢复来路、已经作出的决定和寻找线索。当前路线能够说明怎样接入现有系统并推进用户结果后，才适合扩大实现、专项研究、评审和验证。安全、权限和边界检查仍然保留，但专项调查应由即将执行的行动、当前项目事实或用户授权实际触发。
- **实际修改：** Base 新增独立的“接续现有项目”板块，集中规定新任务重新理解当前项目、用户无需复述可恢复背景、大量项目与历史取证交给相应 subagent、历史原始输出定向读取和扩大工作前验证真实入口。风险触发范围继续保留在通用判断与权限规则中。`code-development` 增加代码阶段的路线门槛，`research-lead` 限制无依据的专项研究。
- **保留边界：** 真实外发、写入、删除、权限变化、不可逆影响和已经观察到的污染仍按原有授权与验证规则处理。项目理解不要求穷尽阅读整个仓库，达到足以判断整体关系和当前路线时停止。
- **验证状态：** 当前完成静态同步。仍需用新的项目接续任务验证模型能否从项目重新建立整体理解，让用户无需补述旧背景，并减少无触发依据的风险扩张与完整历史输出加载。

## R27 阶段报告让用户能够判断方向和进度

- **目标：** 让用户在任务继续扩大前看懂整体进展、当前方向和下一步，能够及时发现偏离并纠正。
- **问题或新证据：** 任务 `01a03e36-e2e8-7cc2-b9ce-a5fc5155b9c9` 和 `01a03e37-a76f-74d1-b640-555566c0c1ae` 的阶段报告主要呈现模块、实现、测试和内部过程，用户无法据此判断整个任务推进到哪里、正在往哪个方向走，也无法在下一轮投入前及时阻止偏离。
- **形成的理解：** 用户可读的阶段报告是任务控制的一部分，不是开发清单。技术修改、测试和 agent 报告用于支持整体状态、方向与下一步的说明，不能代替它。
- **实际修改：** Base 在过程交流中增加计划或阶段完成、准备进入新方向时的状态说明，并要求最终回答先交代用户目标的完成状态、当前可用结果和剩余差距。功能块基线同步更新。
- **保留边界：** 状态报告不增加新的审批步骤。下一步不需要用户决定时继续推进，需要用户决定时沿用现有等待规则。
- **验证状态：** 当前完成文字和静态同步。仍需在新的长任务中验证用户能否仅凭阶段报告判断整体进度、方向和下一步。

## R28 Root Base、Worker Base 与阶段专属提示词物理隔离

- **目标：** Root Base 只承担主 agent 的用户理解、整体路线、跨阶段决定和最终交付；执行型 subagent 收到共同 Worker Base 和角色专属指令，两个阶段负责人分别收到完成本领域阶段所需的完整专属指令。
- **运行时事实：** Codex CLI `0.150.0-alpha.8` 的新任务探针确认，agent TOML 中的 `model_instructions_file` 没有替换父级 Base，两个角色仍看到 Root 规则。该行为与公开问题 [openai/codex#40042](https://github.com/openai/codex/issues/40042) 一致；当前源码的 [`build_agent_spawn_config`](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/multi_agents_common.rs) 复制父级 `BaseInstructions`，而 [`AgentRoleOverrides`](https://github.com/openai/codex/blob/main/codex-rs/core/src/agent/role.rs) 只提供角色级 `developer_instructions` 覆盖，没有传递 `model_instructions_file`。
- **否决路线：** 不再依赖 agent TOML 中看似存在但实际未生效的 `model_instructions_file`，也不使用启动 hook 或常驻脚本在运行时拼接提示词。静态文件存在和 TOML 解析成功不能证明目标模型实际收到正确层级。
- **当前装配：** 全局 `model_instructions_file` 只指向中性 `shared-runtime-base-instructions.md`。全局 `developer_instructions` 只保存与 Root Base 权威源逐字一致的运行时镜像；它位于 Prompt Lab Git 仓库之外，不承担版本历史。命名角色的 `developer_instructions` 替换父级这一层。八个执行角色以内联 Worker Base 开头；`research-lead` 与 `code-executor` 分别保存完整、自包含的专属提示词，不再为了少量共性共享 Stage Base。
- **验证状态：** 上一版真实任务已经证明 Root developer 镜像不会进入使用 `fork_turns: "none"` 的命名角色。2026-08-28 取消共同 Stage Base 后，10 个角色 TOML 静态解析通过，八个 Worker 前缀逐字符一致，两个阶段角色均不含 Worker 前缀并保留各自专属结构；全新任务的两个阶段角色真实加载和行为仍须单独验证，不能沿用旧版前缀测试冒充。
- **维护边界：** 维护者先修改私人 Prompt Lab 权威源，再发布公开正文并安装运行镜像，不得在副本中独立维护；修改 Worker Base 时同步八个执行角色前缀，修改阶段角色时直接维护对应 TOML。当前只有两个方法差异明显的阶段角色，因此不建立共同 Stage Base；将来阶段角色增多并形成真实、无冲突的共同规则时可以重新评估。当前会话已加载的旧提示词不会被热替换，行为验证必须使用新任务。

## R29 Root、阶段负责人和工人的投入责任重新归位

- **目标：** 防止 Root 或阶段负责人把“让当前路线跑通”变成独立目标，同时保留合同内普通工作连续推进，不把每个细节重新交给用户或上级。
- **问题或新证据：** 任务 `01a03e36-e2e8-7cc2-b9ce-a5fc5155b9c9` 中，最小用户结果长期没有出现，Root 仍连续驱动多轮验证、重启、脚本和执行角色，阶段内部又不断提高限制并新增补偿。过程指标和测试增长没有转化为用户结果，说明仅在 Root 写停止线不能约束阶段内扩大，也不能解决 Root 连续管理叶子角色的问题。
- **形成的理解：** 动作级无用功检查属于所有 agent 共同执行层。Root 负责整个任务的压缩理解、用户校准、阶段拆分、整体路线和投入决定。阶段负责人负责一个阶段的核心判断、核心工作、下属整合和验收，并在合同未授权的高成本运行、大范围结构修改或明显增加下属轮次前报告并等待。工人只完成固定合同，遇到同类越界动作直接交回上级。
- **实际修改：** 通用动作门迁入全局 `AGENTS.md`；Root 增加压缩任务状态、小任务直派条件和从叶子波次升级到阶段负责人的条件；阶段 Base 增加投入升级决定包；工人 Base 增加未授权高成本和大范围动作停止线。8 个工人角色与 2 个阶段负责人角色的有效内联镜像同步更新。
- **保留边界：** 多轮工具调用本身不触发阶段负责人。结果、做法和验收固定的单一有界浏览器、取证或执行阶段仍可由叶子角色一次完成；只有方案继续演化、多个下属、共享状态或反复整合才升级。阶段合同已经明确授权的普通工作不逐项上收。

## R30 接续旧任务先校准，阶段报告采用视觉优先教学
