# 安装、配置和 Hook 规则理由

本文件不参与运行。它记录安装合同、示例配置、项目 `AGENTS.md` 模板和全局 Hook 中会改变实际加载或调度行为的规则。安装步骤本身与运行时长期规则分开判断；一次测试没有执行时，准确标为未验证即可。

## RC-01 Root Base 不进入 `model_instructions_file`

- **状态：** `current-effective`
- **行为：** `model_instructions_file` 只加载所有责任层都安全的中性共享 Base。Root Base 通过顶层 `developer_instructions` 镜像只交给 Root。
- **理由：** 当前宿主无法关闭 subagent 对 `model_instructions_file` 的继承。把 Root 的用户理解、整体路线、调度和最终判断放进去，会让阶段负责人和一线执行者收到不属于自己的责任，并破坏分层上下文。
- **案例：** 角色层级混乱后，曾把 Root 的问题误判为 Base 本文问题并发生大范围错误改写；运行时探针确认角色 TOML 不能替换父级这一层。
- **来源：** `INSTALL.md`；`examples/config.toml`；`prompt-lab/subagent-architecture/rule-rationale.md` R32；用户本轮确认。
- **验证：** 静态装配与历史探针支持；每次宿主升级后仍需区分静态文件和 fresh-task 加载。
- **改变条件：** 只有宿主原生提供可靠的 Root-only instruction file，或允许 subagent 明确关闭继承时才改变。

## RC-02 所有内部委派显式使用 `fork_turns: "none"`

- **状态：** `current-effective + unverified`
- **行为：** 委派合同写清目的、背景、行动、结果和边界；不用有限轮次、`all`，也不省略 `fork_turns`。
- **理由：** 标准化合同已经能传递当前责任。有限轮次按时间截取，容易带入无关上下文并产生隐式依赖；`all` 还会继承上级模型和推理强度，直接破坏按能力与成本分层的角色设计。
- **案例：** C-08、C-09、C-10；历史真实调用中 `all` 创建了不符合预期的高成本 subagent。
- **来源：** Root Base R-11；Agent `PROMPT_HISTORY.md`；用户本轮确认。
- **验证：** 提示词和合同结构已存在；当前 Hook 的真实拦截仍见 RC-06。
- **改变条件：** 只有宿主提供更可靠、可复现且不会继承模型配置的结构化上下文传递机制时才复审。

## RC-03 多 agent 最大深度为 2

- **状态：** `current-effective + conditional`
- **行为：** 把 Root 视为第 0 层、阶段负责人视为第 1 层、一线工人视为第 2 层，不再增加第 3 层执行 agent。
- **理由：** 每经过一层摘要和转述，信息都会损失。Root 负责控制整体体系，应尽量接近一线证据；继续增加层级会让 Root 更可能根据失真信息作判断。两层已经允许阶段负责人吸收模块细节并组织工人，同时保留清楚的逐级上报链。
- **案例：** 自由派生实验出现线程超额、无报告和长时间等待；受控的 Root—负责人—工人链路能够完成交回。
- **来源：** `examples/config.toml`；历史 `rule-rationale.md`；用户本轮信息论解释。
- **验证：** 配置值和静态责任链明确；不同规模长任务的质量与成本仍需观察。
- **改变条件：** 只有新的模型或宿主能可靠证明更深层不会降低情报真实性，并且额外层级产生明确收益时才提高。

## RC-04 每个任务最多 10 个并发 agent 槽位

- **状态：** `current-effective + conditional`
- **行为：** `max_concurrent_threads_per_session = 10`，并发结构按实际责任选择，不为凑满槽位创建工作。
- **理由：** 十个槽位能容纳常见的 `3-3-3-1` 或 `3-3-4`：多个阶段负责人各带少量下属，同时保留一个独立 Reviewer 或自由位置。它既能覆盖大型任务的并行需要，也能限制失控派生。
- **案例：** 历史 32 线程配置不能证明当前值；自由派生已经出现超额和等待问题。当前“10”的直接理由来自用户本轮架构说明，而不是旧实验结论。
- **来源：** `examples/config.toml`；用户本轮确认。
- **验证：** 配置静态有效；具体任务不保证需要或能够有效利用十个槽位。
- **改变条件：** 角色结构、宿主并发、成本或真实任务数据变化时可重新计算，不把 10 当作永久常量。

## RC-05 项目 `AGENTS.md` 保存项目范围内的持续指导

- **状态：** `current-effective`
- **行为：** 项目 `AGENTS.md` 保存该仓库或目录的专属工作约定、构建测试与评审要求、权限和兼容边界，并可索引需求、设计、实现入口、验收与当前状态等权威文件。更近目录可以覆盖更广范围的指导。
- **理由：** Codex 会在开始工作前从全局到项目和当前目录组合 `AGENTS.md`。因此这里适合放只有进入该项目才应生效、而且需要跨任务持续读取的背景与规则。文件索引只是降低重新寻找权威来源成本的一种重要用法，不是它的全部用途。
- **案例：** 多 agent 合同使用稳定项目文件传递长期决定；重复保存权威正文曾造成版本漂移。
- **来源：** `examples/project-AGENTS.md`；OpenAI 官方 [Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)；Agent `PROMPT_HISTORY.md`。
- **验证：** 官方加载顺序和静态示例明确；具体项目仍需按自身结构编写。
- **改变条件：** 项目事实可由更可靠的原生项目上下文稳定提供时可以减少索引，但项目专属规则仍放在实际会被相应目录读取的位置。

## RC-06 Hook 拒绝非 `none` 的委派

- **状态：** `current-effective + unverified`
- **行为：** `PreToolUse` Hook 只匹配已确认的 subagent 创建工具名并检查 `fork_turns`；只有精确的 `none` 放行，省略、`all`、有限轮数和其他值返回拒绝。预期拒绝使用 Hook 协议的 `permissionDecision: deny`；脚本自身无法解析输入时以 stderr 和退出码 2 阻断，不把校验失败当作放行。
- **理由：** 提示词能说明选择，却不能机械保证每次工具参数正确。Hook 作为第二层保护，防止一次遗漏直接带入大量父级上下文或错误模型配置。
- **案例：** 2026-08-30 fresh smoke test 中实际工具名为 `multi_agent_v1__spawn_agent`，旧 matcher 没有覆盖，`fork_turns=all` 仍创建了 subagent。当前 matcher 已补入该真实名称；历史别名暂时保留用于兼容已观察到的入口。
- **来源：** `hooks/hooks.json`；`hooks/fork-turns-guard.ps1`；OpenAI 官方 [Hooks](https://learn.chatgpt.com/docs/hooks)；历史 rollout `01a04f09-695b-7b70-898b-14173036b94f`。
- **验证：** `none`、`all`、省略、有限轮数和无关工具的离线输入已经通过；配置采用 5 秒超时，因为脚本只读取一段 JSON 并形成一次本地判断，正常不应接近该时间。matcher 修正后仍需在新的真实任务中确认宿主确实把该协作工具交给 Hook；超时或异常在当前宿主中的实际阻断表现也没有用离线测试证明。
- **改变条件：** 宿主原生禁止非 `none`，或协作工具的 canonical name/Hook 协议变化时更新实现。Hook 失败不能被当作已经阻断。

## RC-07 安装后的真实任务检查是可选验证

- **状态：** `current-effective + conditional`
- **行为：** 安装完成后可以新建 Root、阶段负责人和工人测试任务验证真实加载。用户不希望额外消耗时可以跳过，并在完成报告中把该层标为未验证。
- **理由：** 真实任务只能增加运行时信心，不参与构成安装文件本身；为了测试额外消耗模型额度不是每次都值得。静态写入、TOML 解析和真实加载仍必须作为不同证据层报告。
- **案例：** 历史多次证明静态同步不等于 fresh-task 生效；用户本轮同时确认这一步只是测试，可以不做。
- **来源：** `INSTALL.md`；全局验证责任；用户本轮确认。
- **验证：** 是否执行由当次安装授权和成本决定。
- **改变条件：** 高风险发布、宿主机制变化或用户明确要求真实验收时，把相应测试纳入该次完成条件。
