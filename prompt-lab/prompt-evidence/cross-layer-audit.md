# 提示词跨层保真审查

本文件不参与运行。它检查相近规则为什么出现在不同层、是否真的重复，以及一处删除后是否仍有所有目标角色稳定读取的承载位置。

## 各层只负责什么

| 层 | 当前责任 | 不应接管 |
|---|---|---|
| Root Base | 用户理解、整体路线、用户决定权、团队结构、阶段衔接、成本、最终交付和用户沟通 | 角色内部方法、项目事实、工具 API 细节 |
| 全局 `AGENTS.md` | 所有 agent 都需要的合同执行、责任链、成品、验证和 Windows 安全 | Root 的用户理解、Plan mode、模型成本、具体角色选择 |
| Shared Runtime Base | 同一提示词层内从上位到下位理解规则 | Root 或任何角色的业务职责 |
| Worker Base | 执行型角色共同的有界合同、停止、上交和一次交回 | 阶段规划、用户目标、跨模块决定 |
| 阶段角色 | 一个代码模块或研究阶段的核心判断、组织、整合和验收 | 用户目标、跨阶段路线和最终交付 |
| 执行/检查角色 | 一个已划定的取证、实现、评审、网页操作或黑盒测试责任 | 整体任务和未授权的相邻工作 |
| Skill | 按任务触发的领域方法和所需资源 | 常驻身份、运行时权限和项目专属事实 |
| 项目 `AGENTS.md` | 当前项目专属规则与权威文件索引 | 跨项目通用方法和全局角色定义 |
| 工具与宿主说明 | API 参数、权限、唤醒和真实支持字段 | 用户目标、路线和长期协作偏好 |

## 看起来重复但当前有必要保留

| 相近内容 | 为什么不是可直接删除的重复 |
|---|---|
| Root、全局层和 `code-development` 都有最低复杂度 | Root 选择整体路线；全局层要求每个责任人不在合同内造额外系统；代码 Skill 说明工程中的复用、抽象和维护判断 |
| Root 与全局层都有无用功检查 | Root 控制整体路线、预算和团队扩张；全局层阻止每个 agent 在自己的合同内相同条件重试、等待或扩大 |
| Root、全局层和 Skill 都区分证据层 | Root 用它判断整体完成和用户进度；全局层约束所有完成声明；领域 Skill 说明该领域什么才是直接证据 |
| Root 与两个阶段角色都含完整官方 Skill 使用章节 | 当前运行时命名角色不会可靠继承 Root developer 镜像；三个会选择 Skill 的责任人都必须直接收到完整协议，摘要实验已经失败 |
| Worker Base 在八个 TOML 中逐字内联 | 角色级 `model_instructions_file` 当前不生效；内联是运行时实际加载所需的镜像，共同文件只是维护源 |
| Root 与两个阶段角色都写 `fork_turns: "none"` | Root 可以直接委派，两个阶段负责人可以继续向下委派；没有调度权的执行角色不需要这条规则 |
| Root 的基本用户理解与 `workflow-state-distiller` | Root 总是维护最小当前状态；只有状态散乱到不能可靠指导下一步时才加载 Skill 做完整蒸馏校准 |
| Root 的阶段报告触发与 `eli5` | Root 决定何时需要帮助用户重获全局视野；Skill 决定怎样按受众和信息结构解释 |
| Root 的提问规则与 `product-development` | Root 处理所有任务的决定权和高价值校准；产品 Skill 处理客户现实、问题定义、产品路线和产品实验 |
| `deep-research` 与 `search-source-registry` | Deep Research 决定何时做开放多路线研究、怎样发散和综合；来源注册表决定从哪些入口开始、怎样记录来源覆盖和失败 |
| `code-development` 与来源注册表的代码 reference | Code Development 负责工程路线、实现、集成和交付；代码来源表只帮助联网发现与核验成熟候选 |

## 本轮发现并处理的真实缺口

1. Root Base 只有核心规则理由，没有覆盖决策支持、Plan mode、调查停止、换路权限、交付、写作、新消息和上下文压缩。现已增加 R-17 至 R-24 和全文覆盖索引；未改 Root 正文。
2. 全局 Windows 规则曾被 G-10 一段概括，无法保护每个高风险护栏。现已逐项记录 PowerShell 版本、执行策略、引用、错误码、编码、系统变量、Git 凭据、路径解析和破坏性文件操作原因；未改全局正文。
3. Agent 理由没有完整解释 Reviewer、Web Researcher 的模型强度和各角色能力关闭项。现已增加 A-15、角色模型理由和逐文件覆盖索引；未借机改写其他角色正文。
4. 公开 `visual-usability-tester.toml` 和 `agents/README.md` 落后于用户确认的本机版本。现已从本机向公开仓库同步，未反向覆盖。
5. `search-source-registry` 是通用研究基础，却只存在于本机安装目录。现已审计正文、备份、references 和 scripts，并将运行文件与规则理由纳入公开仓库；历史备份不进入发行目录。
6. `workflow-state-distiller` 的保存位置章节在旧维护记录和当前正文之间冲突。用户已确认保留，但它只是附带作用；主目的仍是蒸馏和校准。状态已写回 CHANGELOG、理由和案例 C-26。

## 本轮没有当成缺口的内容

- 阶段角色没有复制 Root 的“新模块形成新阶段合同”。阶段负责人只管理当前阶段和允许的叶子执行者，新阶段由 Root 创建；全局责任链已经要求合同外问题上交。
- Explorer、Web Researcher、Worker 和 Worker Luna 关闭 Skill 指令注入不是遗漏。它们获得做法或取证边界已经确定的合同；需要选择领域方法的责任留在 Root 或阶段负责人。
- 共同 Stage Base 当前没有建立，是因为只有两个阶段负责人且领域方法不同。未来角色增多并出现真实共享规则时可以重新评估，不是永久禁止。
- `company-research-brief` 没有纳入公共体系不是遗漏。用户确认它是给风投同事的旧 Skill，已经久未维护，未来应作为独立产品任务重做。
- 外部、官方或来源未知的 Skill 不建立用户规则理由，只记录来源、版本和本地漂移。

## 仍需真实验证的部分

- 全新 Root、阶段负责人和执行角色是否实际加载当前层级与能力开关。
- `fork_turns: "none"` Hook 在 Codex Desktop 的真实调用路径是否拦截省略参数和 `all`。
- 新的 Code Executor → Worker/Reviewer/Visual Tester 完整闭环是否降低 Root 唤醒、时间和 Token。
- Worker Luna 当前速度、正确率、返工次数和 Root 唤醒成本是否仍接近当初的优化目标。
- Visual Usability Tester 的 Browser/Computer Use 继承和 Luna low 黑盒行为。
- `search-source-registry` 的实时来源可访问性、候选召回和网络 API 变化。
- `frontend-design`、`markitdown-files` 的上游来源，以及 `resume-jd-optimizer-cn` 的版本冲突。

这些未验证项不能通过继续改提示词正文解决。它们应在相应真实宿主、模型或网络任务中取得证据后，再决定是否需要局部修正。
