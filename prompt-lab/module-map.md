# 当前 Base 的规则地图

## 规则分层

提示词活在整个 agent 调用里，Base 不能作为孤立文件优化。先看完整调用已经提供哪些能力，工具、角色、宿主或自动注入层已经可靠产生的行为不再写进 Base，只补足整个调用仍然缺少的判断。

- **运行时与工具：** 工具参数、唤醒方式、固定输出格式和宿主交互由工具说明与应用上下文保证。
- **Base：** 保留所有任务都会用到的工作循环、用户理解、路线与授权判断、Root 调度和交流规则。
- **AGENTS.md：** 保留团队共同执行机制、成品与验证责任，以及文件、Shell、Windows、内部通信等工作环境规则。
- **Skill：** 按任务渐进加载领域方法，例如代码开发、研究、批处理和提示词维护。
- **Agent：** 保留角色内部怎样完成责任、管理下属和形成交回结果的规则。

Root 必须据此选择路线或责任人的触发条件留在 Base。工具已经完成的约束不改写成提示词，只影响某类任务的步骤放进 Skill，只影响一个角色内部工作的步骤放进 Agent，团队共同执行细节放进 AGENTS.md。

## 维护材料

- `codex_base_instruction_5.6.md` 是当前运行版，也是现行 Base 规则的权威文本。
- `functional-block-baseline.md` 保存各功能面的保真基线，用于模型或宿主变化后的恢复和测试，不直接替换运行版。
- 修改记录、只读备份和 Git 保存规则的形成理由与精确版本，不进入日常运行上下文。

## Base 保留的功能块

- 主 agent 的总体责任和四步工作循环。
- 理解用户、提问、接续项目、补足信息和形成判断。
- 工作路线、下一步计划、成熟做法和受阻换路。
- 用户授权和需要用户决定的变化。
- 团队结构、责任划分、角色路由、结果交回层级和委派后的整合。
- 交付、过程交流、最终回答和 Skill 入口。

工具已经规定的参数和输出格式，以及具体命令写法、文件操作流程、代码开发阶段、浏览器页面操作和各角色内部管理不在 Base 展开。

## 多 agent 规则的装配

- 根据依赖、共享状态和角色能力选择最简单的执行结构。
- 需要多轮工具调用或大量输入输出的完整责任交给职责匹配的角色，具体选择由当前注册的角色说明提供。
- 已经交出的责任由对应角色完成，Root 不管理中间步骤。
- 同一责任使用 `followup_task` 继续，新责任使用 `spawn_agent`，没有其他可以推进的工作时使用 `wait_agent`。
- 完整报告有合同和证据支持时直接采用，只在具体矛盾、关键证据缺口或较高错误代价下定向核验。

## 修改条件

修改 Base 时先确认问题是否跨任务发生，以及 Root 是否必须知道这条规则才能行动。几条规则能够由一次工具调用或现有机制直接产生同样行为时，直接使用该机制并删除规则。只剩一个未被机制覆盖的判断时，Base 只写这个触发或决定。

Base 依赖的共同层、角色和 Skill 必须随体系一起保存和安装，不能形成只在作者机器上成立的隐藏依赖。

删减前用运行版、功能块基线、修改记录和真实任务证据确认规则的原始作用。高风险规则保留明确边界，交互规则根据持续用户反馈修改，不从单次静态判断重写整个分区。
